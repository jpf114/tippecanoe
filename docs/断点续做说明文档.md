# Tippecanoe 断点续做（Checkpoint / Resume）

本文档说明原生 `tippecanoe`（GeoJSON / CSV / FlatGeobuf 等读入路径）的 **zoom 级断点续做** 功能。
**不包含** `tippecanoe-db`（PostGIS / Mongo 等），后者在后续版本中再考虑。

> **重要**：本文档描述的是 **自包含 resume（self-contained resume）** 设计。
> 续跑时只需 `--resume=DIR` 一个参数，所有必要的输出路径、zoom 范围、输入文件列表均从 checkpoint 目录自动恢复，无需在命令行重复传入。

> **架构变更（v2）**：从 v2 起，checkpoint 状态存储从 SQLite 改为 **纯文件系统方案**（`state.json` + 原子 `rename`），消除了 SQLite WAL/Journal 的崩溃窗口，不再依赖 SQLite 作为状态账本。SQLite 仅用于 mbtiles **输出格式** 的 WAL 清理。

> **架构变更（v3）**：v3 在 v2 基础上引入 **数据完整性校验** 与 **磁盘空间保护**：
> - **CRC32 校验**：所有 blob 文件末尾追加 IEEE 802.3 CRC32（4 字节），resume 时自动校验数据完整性，防止磁盘静默错误导致续跑产生损坏瓦片。
> - **磁盘空间预算检查**：`snapshot_tiling_entry` / `on_zoom_complete` 前先调用 `statfs` 检查剩余空间，不足时以 `EXIT_CHECKPOINT=121` 退出，避免写到一半才报 `ENOSPC`。
> - **世代清理索引化**：`state.json` 增加 `current_gen_files` 字段，记录当前 generation 的文件列表，使旧代数清理从 O(n) 目录扫描降为 O(1) 直接 unlink。
> - **自适应 bloom filter**：`shared_nodes_bloom` 大小根据 `nodepos` 动态调整（1MB ~ 64MB），小数据集不浪费内存，大数据集保持假阳性率 < 1%。
> - **异步 fsync**：blob 目录 fsync 在 detached 线程中执行，不阻塞 `on_zoom_complete` 主线程。
> - **指纹内容哈希**：对 < 100MB 的输入文件计算 SHA-256 内容哈希，纳入 fingerprint，防止 mtime/size 碰撞导致错误 resume。
> - **向后兼容**：v3 代码可读取 v2 state.json（新字段缺省为空/零），v2 blob 文件（无 CRC32 后缀）也能正常读取，只是不校验 CRC。

## 1. 功能概述

在生成矢量瓦片时，任务往往耗时很长（读入大 GeoJSON、多级 zoom 切片）。进程被 `kill -9`、OOM 或机器重启打断后，传统做法只能从头重跑。

断点续做提供：

- **专用 checkpoint 工作目录**（与 `-o` / `-e` 输出路径分开）；
- **每个 zoom 成功结束后** 落盘中间状态；
- **自包含 `--resume=DIR`** 时跳过读入与 radix，从「上一完成 zoom 的下一级」继续切片；
- **自动清理 kill -9 残留**：WAL/SHM/JOURNAL 文件、未提交 zoom 的瓦片、未提交 zoom 的目录；
- **自动恢复 metadata**：`bounds` / `center` / `antimeridian_adjusted_bounds` / `vector_layers` / `tilestats` 与正常路径完全一致；
- **SIGTERM/SIGINT 优雅退出**：收到信号后完成当前 zoom 再退出，checkpoint 已保存；
- **flock 并发锁**：防止多个进程同时 resume 同一 checkpoint；
- **进度报告**：每个 zoom 完成后打印百分比和预估剩余时间；
- **管理命令**：`--checkpoint-status=DIR` 查询状态，`--checkpoint-prune=DIR` 清理 blobs；
- **CRC32 数据完整性校验**（v3）：blob 文件末尾追加 CRC32，resume 时自动校验，防止磁盘静默错误；
- **磁盘空间预算检查**（v3）：写入前预检 `statfs`，空间不足立即以 `EXIT_CHECKPOINT=121` 退出；
- **世代清理索引化**（v3）：`current_gen_files` 字段使旧代数清理从 O(n) 目录扫描降为 O(1) unlink；
- **自适应 bloom filter**（v3）：根据预期节点数动态调整 bloom 大小（1MB ~ 64MB）；
- **异步 fsync**（v3）：blob 目录 fsync 在后台线程执行，不阻塞主线程；
- **指纹内容哈希**（v3）：对 < 100MB 的输入文件计算 SHA-256，纳入 fingerprint 防止 mtime/size 碰撞。

### 1.1 两阶段模型（必读）

| 阶段 | 内容 | 是否 checkpoint |
|------|------|-----------------|
| **阶段 A** | 读入 GeoJSON、radix 排序、合并 stringpool、建 shared_nodes 等 | **否** |
| **阶段 B** | `traverse_zooms`：按 zoom 写 mbtiles 或目录瓦片 | **是**（每 zoom 一次） |

因此：

- 中断发生在 **读入 / 排序** 时：checkpoint 目录里通常还没有可用的「切片入口快照」，下次只能 **全量重跑**（与计划一致）。
- 中断发生在 **切片过程中**：已完成的 zoom 有记录，且已保存进入下一 zoom 所需的 geom 分片与 stringpool，可 **`--resume` 续跑**。

「zoom 级」**不是**「只记录 mbtiles 里已有哪些 z」，而是必须保存 **算法中间态**（否则无法从 z+1 继续，因为 z+1 的输入来自 z 结束时生成的 geom 分片，且属性索引依赖同一次读入的 stringpool）。

## 2. 设计原理

### 2.1 核心架构：纯文件系统 + 原子 rename

| 内容 | 存储位置 | 原因 |
|------|----------|------|
| 作业指纹、命令行、zoom 进度、时间戳 | `state.json` | 纯文本 JSON，原子 rename 更新，无 SQLite 依赖 |
| stringpool、geom 分片、shared_nodes、bloom、file_bbox | `blobs/` 下普通文件 | 可达 GB 级；使用 `mmap` 直接映射 |
| 写入中的数据 | `staging/` | 写完后 `rename` 到 `blobs/`，再更新 state.json |
| 并发锁 | `.lock` 文件 + `flock` | 防止多进程同时 resume |
| zoom 完成标记 | `commits/zoom-N.done` | 防御性校验，证明 zoom 已提交 |

**纯文件系统方案的核心思想**：

- **state.json**：人类可读的 JSON 格式，记录所有元数据（指纹、命令行、zoom 进度等）；
- **原子 rename**：更新 state.json 时，先写 `state.json.tmp`，`fsync` 后 `rename` 覆盖 `state.json`，再 `fsync` 目录。`rename()` 在同一文件系统上是原子操作，保证 `kill -9` 后 state.json 始终是完整的旧版本或完整的新版本，**不会出现半截状态**；
- **无 SQLite 状态依赖**：消除了 SQLite WAL/Journal 的崩溃恢复窗口，不再需要 `PRAGMA` 回滚热日志等复杂操作（但仍需清理 mbtiles 输出文件的 WAL）。

**v1 → v2 架构变更理由**：

| 维度 | v1（SQLite） | v2（纯文件系统） |
|------|-------------|-----------------|
| 崩溃一致性 | 依赖 WAL/Journal 回滚，有热日志窗口 | `rename` 原子，无回滚窗口 |
| 并发控制 | SQLite 自带锁 | `flock(LOCK_EX\|LOCK_NB)` |
| 可读性 | 需 `sqlite3` 命令查询 | 人类可读 JSON |
| 依赖 | 需要 SQLite 库 | 无额外依赖 |
| 调试 | 需要 SQL 知识 | `cat state.json` 即可 |
| 写入开销 | 事务 + WAL 刷盘 | `fwrite` + `fsync` + `rename` |

### 2.2 原子提交顺序（防止半截状态）

每个 zoom 的 `commit` 顺序为：

1. 将新的 geom 分片（`geom.{slot}.g{gen}`）、`skip_children`、`strategies` 写入 `staging/`；
2. 对相关文件 `fsync`；
3. **原子 `rename`** `staging/` → `blobs/`：
   - 有新数据的文件：`rename()` 原子替换旧版本；
   - 无新数据的 slot：不写文件（该 slot 的旧 gen 文件稍后清理）；
4. 清理旧代数（old generation）的 geom 文件；
5. **`fsync` blobs/ 目录**：确保 rename 操作持久化到磁盘；
6. **原子更新 state.json**（`save_state_atomic`）：
   - 序列化 `CheckpointState` 为 JSON 字符串；
   - 写入 `state.json.tmp`；
   - `fflush` → `fsync` → `fclose`；
   - `rename(state.json.tmp, state.json)`；
   - `fsync` checkpoint 目录；
7. 创建 `commits/zoom-N.done` 标记文件（防御性校验）；
8. 调用 `report_progress(z)` 打印进度。

**关键设计**：步骤 3 中 **不先删除旧 blob 再 rename**，而是直接 `rename` 覆盖。若先删后写，在 `kill -9` 后 `blobs/` 中可能为空，导致 resume 失败。`rename()` 原子替换保证 `blobs/` 中始终存在有效版本。

步骤 6 的 `state.json.tmp → rename → state.json` 确保 state.json **要么是旧状态（上一个 zoom 的 commit），要么是新状态（当前 zoom 的 commit）**，不会出现中间态。这是 v2 相对 v1 的核心优势：不依赖数据库引擎的崩溃恢复机制。

仅在当前 zoom 的 drop 多 pass 循环 **全部成功**（`again == false`）且 `err == INT_MAX` 时调用 `on_zoom_complete`，避免「重试中」的错误进度。

### 2.3 文件代数（generation）机制

geom 分片文件使用 **代数后缀** 命名，避免 rename 覆盖旧文件时的竞态问题：

| 文件名 | 含义 |
|--------|------|
| `geom.initial` | 初始快照（阶段 A 完成后写入一次，未压缩） |
| `geom.{slot}.g{gen}` | 第 `gen` 代、第 `slot` 个分片（每个 zoom 完成后写入，压缩格式） |

- `slot` 范围：`0 .. TEMP_FILES-1`（`TEMP_FILES = min((MAX_FILES-10)/2, CPUS*4)`）；
- `gen` 是递增计数器，每次 `on_zoom_complete` 时 `+1`；
- resume 时从 `state_.generation` 读取最新代数，加载对应代数的所有 geom 文件；
- 旧代数文件在新代数文件安全 rename 到 `blobs/` 后才被清理。

### 2.4 并发锁（flock）

防止多个进程同时 resume 同一 checkpoint 目录：

```
acquire_lock():
  1. 创建 {dir}/.lock 文件
  2. flock(lock_fd, LOCK_EX | LOCK_NB)
     ├── 成功 → 获得锁，继续
     └── 失败 (EWOULDBLOCK) → fprintf(stderr, "checkpoint is locked by another process") → exit(EXIT_EXISTS)

release_lock():
  1. flock(lock_fd, LOCK_UN)
  2. close(lock_fd)
  3. unlink({dir}/.lock)  （在 finalize_success 或析构时调用）
```

锁是 **建议性锁**（advisory lock），仅对 cooperate 的进程生效。`LOCK_NB`（非阻塞）确保获取不到锁时立即退出而非死等。

### 2.5 SIGTERM/SIGINT 优雅退出

通过 `install_signal_handlers()` 注册信号处理器：

```cpp
volatile sig_atomic_t g_shutdown_requested = 0;

void signal_handler(int sig) {
    (void) sig;
    g_shutdown_requested = 1;
}

void install_signal_handlers() {
    struct sigaction sa;
    sa.sa_handler = signal_handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigaction(SIGTERM, &sa, NULL);
    sigaction(SIGINT, &sa, NULL);
}
```

在 `traverse_zooms` 的 zoom 循环中，每个 zoom 完成后检查 `shutdown_requested()`：

```cpp
// tile.cpp, traverse_zooms() 循环末尾
if (checkpoint::shutdown_requested()) {
    fprintf(stderr, "\nShutdown signal received; stopping after zoom %d.\n", z);
    break;
}
```

**行为**：

- 收到 SIGTERM/SIGINT 后，**不会立即退出**，而是完成当前 zoom 的切片和 checkpoint 提交后，在下一个 zoom 开始前退出；
- checkpoint 状态已通过 `on_zoom_complete` 保存，下次 `--resume` 可从断点继续；
- 退出码为 `EXIT_INCOMPLETE`（100），表示瓦片未全部完成但 checkpoint 可用；
- SIGKILL（kill -9）无法被捕获，仍需依赖 checkpoint 的崩溃一致性。

替代 `system("rm -rf")`，消除命令注入风险：

用于 `clear_workspace()`、`cleanup_resume_dirs()` 和 `checkpoint_prune()`。

### 2.7 sendfile 零拷贝

`copy_fd_to_file` 改进：

- **Linux**：优先使用 `sendfile()` 零拷贝（内核空间直接传输，无用户态缓冲）；
- **其他平台 / sendfile 失败**：回退到 `read` + `write` 循环，1MB 缓冲区（原 64KB）；
- 拷贝完成后 `fsync` 目标文件；
- 保存并恢复源 fd 的偏移量（`lseek`），不影响后续读取。

### 2.8 与切片算法的关系

- **不修改** `write_tile`、drop/coalesce、几何切分、radix 等核心逻辑；
- 仅在 `traverse_zooms` 循环末尾增加 **两处** 钩子：`on_zoom_complete` 调用 + `shutdown_requested` 检查，具体逻辑在 `checkpoint.cpp`；
- `main.cpp` 的 `read_input` 首尾负责「是否跳过读入」与 `snapshot_tiling_entry`。

### 2.9 作业指纹（fingerprint）

指纹是一个 **SHA-256 哈希值**，存储在 `state.json` 的 `fingerprint` 字段。

#### 2.9.1 指纹的用途

**重要**：指纹仅用于校验 **checkpoint 状态的内部一致性**，**不校验** resume 命令行参数。

续跑时，`verify_fingerprint_internal()` 的行为：

1. 从 `state_` 读取 `normalized_cmd`、`output_mode`、`output_path`、`temp_files`、`cpus`；
2. 从 `state_.input_files` 读取所有输入文件的 `path`、`size`、`mtime_sec`、`mtime_nsec`，以及 v3 新增的 `content_hash`（若存在）；
3. 用这些 **存储的值** 重新计算指纹；
4. 与 `state_.fingerprint` 中存储的值比较。

由于步骤 1-2 使用的全是 state.json 中存储的值（而非当前命令行或磁盘上文件的 stat），因此这个校验确保的是「checkpoint 状态没有被外部篡改或损坏」，而不是「当前 resume 命令行与首次运行一致」。

#### 2.9.2 参与哈希的内容

- 格式版本 `TIPPECANOE_CHECKPOINT_FORMAT`（当前为 `3`）；
- **规范化后的命令行**（已剔除 `--checkpoint-dir`、`--resume`、`--checkpoint-force`、`--checkpoint-status`、`--checkpoint-prune`、`-F`、`-f` 等标志）；
- 输出模式（`mbtiles` / `directory` / `pmtiles`）与 **输出路径绝对路径**；
- `TEMP_FILES`、`CPUS`；
- `prevent[]` / `additional[]` 标志位；
- 输入文件列表：`绝对路径 + size + mtime`（排序后）；
- **v3 新增**：对 < 100MB 的输入文件，额外计算 SHA-256 `content_hash` 纳入指纹。这解决了「文件被原地替换但 mtime/size 巧合相同」导致错误 resume 的隐患。大文件（≥ 100MB）不计算内容哈希以避免 I/O 开销，仍依赖 mtime + size 判定。

#### 2.9.3 命令行规范化规则

| 标志 | 处理方式 | 说明 |
|------|----------|------|
| `--checkpoint-dir=DIR` | 整体移除 | 等号形式，标志含参数 |
| `--checkpoint-dir DIR` | 标志和参数均移除 | 空格形式，需跳过下一个 token |
| `--resume=DIR` | 整体移除 | 等号形式 |
| `--resume DIR` | 标志和参数均移除 | 空格形式 |
| `--checkpoint-status=DIR` | 整体移除 | 等号形式 |
| `--checkpoint-prune=DIR` | 整体移除 | 等号形式 |
| `--checkpoint-force` | 移除 | 无参数标志 |
| `-F` / `--allow-existing` | 移除 | 无参数标志 |
| `-f` / `--force` | 移除 | 无参数标志 |

#### 2.9.4 指纹不匹配的后果

指纹不匹配（仅当 checkpoint 状态被外部篡改或损坏时才会发生）会以退出码 `101`（`EXIT_ARGS`）失败并打印 stored / expected 指纹。

### 2.10 关键算法逻辑

#### 2.10.1 `copy_fd_to_file` — fd 到文件的安全拷贝

`on_zoom_complete` 需要将 `geomfd[j]` 的内容拷贝到 `blobs/geom.{slot}.g{gen}`。由于 `geomfd[j]` 同时被 `traverse_zooms` 后续代码使用（`fdopen(geomfd[j], "rb")` 读取），拷贝过程必须 **保存并恢复文件偏移量**：

```
saved_pos = lseek(fd, SEEK_CUR)     // 保存当前偏移量
lseek(fd, 0, SEEK_SET)              // 回到文件头
sendfile(dest, fd, ...)             // Linux: 零拷贝
  或 read(fd, ...) → write(dest, ...) // 回退: 1MB 缓冲区
fsync(dest)                         // 确保数据落盘
lseek(fd, saved_pos, SEEK_SET)      // 恢复原始偏移量
```

若不恢复偏移量，`read()` 会将 fd 偏移量推到文件末尾，导致后续 `fdopen()` 读不到任何数据。

#### 2.10.2 `compressed` 标志的正确计算

在 `traverse_zooms` 中，z0 的数据是未压缩的（排序和 maxzoom 修正需要操作原始数据），z1+ 的数据是压缩的。resume 时从 `last_completed_zoom + 1` 开始，该 zoom 的输入来自上一级 `on_zoom_complete` 保存的压缩数据，因此：

```
compressed = (z > 0)    // z0 未压缩，z1+ 均为压缩
```

注意：不能使用 `compressed = (z != iz)`，因为当 `iz > 0`（resume 起始 zoom）时，`z == iz` 会导致 `compressed = false`，从而错误地按未压缩格式读取压缩数据。

#### 2.10.3 `skip_children` / `strategies` 的容错读取

`read_skip_children_blob` 和 `read_strategies_blob` 在文件不存在时 **优雅返回**（空集合），而非 `exit(EXIT_OPEN)`。原因：若进程在第一个 zoom 完成前被 `kill -9`，`blobs/` 中尚无这两个文件，但 `stringpool` 和 `geom.initial` 已存在，resume 仍应可以继续。

#### 2.10.4 `file_bbox` 持久化与 metadata 重建

为使 resume 后的 `metadata.bounds` / `antimeridian_adjusted_bounds` 与正常路径完全一致，checkpoint 持久化了三个 z=32 像素坐标的全局 bbox：

| 文件 | 含义 | 默认值 |
|------|------|--------|
| `file_bbox.bin` | 数据的全局 bbox（z=32 像素坐标） | `{UINT_MAX, UINT_MAX, 0, 0}` |
| `file_bbox1.bin` | 标准 -180~180 世界面的 bbox | `{0xFFFFFFFF, 0xFFFFFFFF, 0, 0}` |
| `file_bbox2.bin` | 0~360 世界面的 bbox（用于跨日期线检测） | `{0x1FFFFFFFF, 0xFFFFFFFF, 0x100000000, 0}` |

resume 时 `restore_tiling()` 读取这三个文件，`main.cpp` 的 resume 路径用它们通过 `tile2lonlat(z=32)` 重建经纬度 bbox，逻辑与正常路径完全一致。

#### 2.10.5 `layermaps.bin` 格式 v3

为使 resume 后的 `metadata.json`（`vector_layers` + `tilestats`）与正常路径完全一致，layermaps blob 格式已升级到 v3：

| 版本 | 字段布局 |
|------|----------|
| v1 | `segs, [layers, [(nlen, name, id, minz, maxz)]]` |
| v2 | v1 + `points, lines, polygons, retain` |
| **v3** | v2 + `description` + 完整 `tilestats`（含 `min`/`max`/`type`/`sample_values`） |

v3 格式使 resume 路径能够完整重建 `layermap_entry` 的所有字段，从而生成与正常路径字节级一致的 `vector_layers` 和 `tilestats` JSON。

**版本兼容性**：若 `layermaps.bin` 的版本号不等于 3（例如旧版本生成的 v1/v2 文件），`read_layermaps_blob` 会打印警告并返回空 layermaps。此时瓦片内容不受影响，但 `metadata.vector_layers` 和 `metadata.tilestats` 会为空。建议使用 v3 兼容的二进制从 scratch 重跑以获得完整 metadata。

#### 2.10.6 `cleanup_resume_wal` 的热日志回滚流程

进程被 `kill -9` 后，mbtiles **输出文件**可能处于不一致状态：WAL/SHM 文件残留、可能存在热日志（hot journal，记录未完成的事务）。

**注意**：此函数操作的是 mbtiles 输出文件（SQLite 格式），不是 checkpoint 状态。checkpoint 状态本身已通过原子 rename 保证一致性，无需 WAL 回滚。

**正确的清理顺序**（`cleanup_resume_wal` 实现）：

1. **删除 WAL/SHM 文件**：`unlink(*-wal)`、`unlink(*-shm)`；
2. **重置 DB header**：若文件偏移 18-19 处的 magic 为 `0x02 0x00`（WAL 模式），改为 `0x01 0x00`（DELETE 模式）；
3. **打开数据库回滚热日志**：`sqlite3_open()` + `busy_timeout(30s)` + `PRAGMA journal_mode=DELETE`；SQLite 会自动检测并回滚热日志中的未完成事务；
4. **关闭数据库**；
5. **删除 -journal 文件**：回滚完成后，热日志应已被 SQLite 自动清理；`unlink(*-journal)` 清除任何残留。

**关键**：步骤 1 中 **不能** 先删除 `-journal` 文件。若先删 journal，SQLite 打开数据库时无法回滚未完成事务，后续 `PRAGMA` 执行会报 `database is locked`（退出码 116）。必须先让 SQLite 回滚，再清理 journal。

#### 2.10.7 进度报告

`on_zoom_complete` 末尾调用 `report_progress(z)`，输出格式：

```
[checkpoint] zoom 11/12 committed (92%), elapsed 2s, est. remaining 0s
```

- 百分比 = `completed / total * 100`（基于 zoom 完成数，非数据量）；
- `elapsed` 从 `open_new` / `open_resume` 时记录的 `start_time_` 计算；
- `est. remaining` 基于平均每 zoom 耗时预估。

### 2.11 v3 数据完整性校验（CRC32）

#### 2.11.1 CRC32 实现与位置

v3 为所有 blob 文件追加 **IEEE 802.3 CRC32**（与 zlib `crc32` 兼容）4 字节后缀，用于检测磁盘静默错误（bit rot、坏扇区、控制器故障）。

- **CRC32 表**：在 `checkpoint.cpp` 中实现 `init_crc32_table()` + `crc32_compute()`，多项式 `0xEDB88320`；
- **写入位置**：`write_blob_file_with_crc()` / `write_blob_with_crc()` 在数据末尾追加 4 字节小端 CRC32；
- **校验位置**：
  - `read_blob_with_crc()`：读取整个文件，校验末尾 CRC32，返回去掉 CRC 的 data 部分；
  - `verify_mmap_crc()`：对 mmap 区域直接校验（用于 stringpool、shared_nodes、geom 等大文件）。

#### 2.11.2 CRC32 与 mmap 的兼容

由于 mmap 需要映射整个文件（包含 CRC32 后缀），v3 在 restore 时采取「映射整个文件，但 data 长度减 4」的策略：

```
file_size = stat(...).st_size
data_size = blob_has_crc() ? file_size - 4 : file_size
mmap(NULL, file_size, PROT_READ, ...)   // 映射整个文件
verify_mmap_crc(mapped, file_size, ...)  // 校验末尾 4 字节 CRC
// 后续代码使用 mapped[0..data_size) 作为实际数据
```

#### 2.11.3 向后兼容（v2 → v3）

`blob_has_crc()` 方法检查 `state_.format_version >= 3`：
- **v3 state.json + v3 blob**：正常校验 CRC32；
- **v3 state.json + v2 blob**（不可能发生，因为 v3 写 state.json 前必先写 v3 blob）；
- **v2 state.json + v2 blob**：`blob_has_crc()` 返回 false，跳过 CRC 校验，整个文件作为 data；
- **v2 state.json + v3 blob**（不可能发生）。

因此 v3 代码可安全读取 v2 checkpoint，只是不校验 CRC32。

### 2.12 v3 磁盘空间预算检查

#### 2.12.1 检查时机

v3 在两处关键写入点前调用 `check_disk_space(required_bytes)`：

1. **`snapshot_tiling_entry`**：估算 `pool_size + geom_size + nodepos + bloom_size + 64MB` 缓冲；
2. **`on_zoom_complete`**：估算 `sum(geom_size[j]) + 32MB` 缓冲（含 skip_children、strategies、state）。

#### 2.12.2 实现细节

```cpp
bool Session::check_disk_space(int64_t required_bytes) const {
    struct statfs st;
    if (statfs(dir_.c_str(), &st) != 0) {
        return true;  // 无法检查时允许继续（保持原有行为）
    }
    int64_t avail = (int64_t) st.f_bsize * (int64_t) st.f_bavail;
    if (avail < required_bytes) {
        fprintf(stderr, "... disk space insufficient ...\n");
        return false;
    }
    return true;
}
```

- 使用 `statfs`（Linux）或 `statvfs`（BSD/macOS）获取文件系统剩余空间；
- `f_bavail`（普通用户可用）而非 `f_bfree`（含 root 保留块）；
- 检查失败时以 `EXIT_CHECKPOINT=121` 退出，避免写到一半才报 `ENOSPC`。

### 2.13 v3 世代清理索引化

#### 2.13.1 问题背景

v2 的 `on_zoom_complete` 需要清理旧代数的 `geom.*.g*` 文件，采用 **O(n) 目录扫描**（`opendir` + `readdir` 遍历 `blobs/`）。当 `TEMP_FILES` 较大（如 2000）且历史代数较多时，扫描开销不可忽视。

#### 2.13.2 v3 索引化方案

v3 在 `state.json` 中增加 `current_gen_files` 字段，记录当前 generation 的所有文件名：

```cpp
// on_zoom_complete 写入新文件后
state_.current_gen_files = std::move(new_gen_files);  // 直接记录文件名列表

// 下次清理时，直接遍历 current_gen_files 逐个 unlink
for (auto const &old_name : state_.current_gen_files) {
    if (is_current_gen(old_name)) continue;
    unlink((dir_ + "/blobs/" + old_name).c_str());
}
```

清理复杂度从 **O(blobs 目录文件数)** 降为 **O(当前 generation 文件数)**，通常为 `TEMP_FILES` 个文件。

#### 2.13.3 向后兼容

若 `state_.current_gen_files` 为空（v2 state.json），自动回退到 `opendir` 扫描逻辑。

### 2.14 v3 异步 fsync

#### 2.14.1 问题背景

`on_zoom_complete` 中 `fsync(blobs_dir_fd)` 是同步操作，在大目录或慢盘上可能阻塞主线程数百毫秒，影响下一 zoom 的启动延迟。

#### 2.14.2 v3 异步方案

```cpp
void Session::async_fsync_blob_dir() {
    std::string blobs_dir = dir_ + "/blobs";
    std::thread([blobs_dir]() {
        int fd = open(blobs_dir.c_str(), O_RDONLY | O_DIRECTORY);
        if (fd >= 0) {
            fsync(fd);
            close(fd);
        }
    }).detach();
}
```

- 使用 `std::thread` + `detach()`，主线程立即返回；
- blob 文件本身的 `fsync(fp)` 仍是同步的（在 `fclose` 前），确保数据已落盘；
- 异步的只是 **目录元数据** 的 fsync，即使丢失也只是目录条目未刷新，不影响文件内容（文件内容已通过文件级 fsync 落盘）。

### 2.15 v3 自适应 bloom filter

#### 2.15.1 问题背景

v2 的 `shared_nodes_bloom` 固定大小，对小数据集浪费内存，对大数据集假阳性率过高。

#### 2.15.2 v3 自适应方案

```cpp
size_t estimated_nodes = nodepos / sizeof(node);  // 预期节点数
size_t bloom_size = estimated_nodes / 2;          // 约 8 bits per node，假阳性率 ~1%
if (bloom_size < 1 * 1024 * 1024)  bloom_size = 1 * 1024 * 1024;   // 最小 1MB
if (bloom_size > 64 * 1024 * 1024) bloom_size = 64 * 1024 * 1024;  // 最大 64MB
if ((bloom_size & (bloom_size - 1)) == 0) bloom_size += 12345;     // 避免 2 的幂
shared_nodes_bloom.resize(bloom_size);
```

- **估算依据**：`nodepos` 是 `shared_nodes` 文件大小，`sizeof(node)` 是单节点字节数，`nodepos / sizeof(node)` 即去重前的节点数；
- **8 bits per node**：理论假阳性率约 0.8%（Bloom filter 经验值）；
- **最小 1MB**：避免极小数据集的 bloom 过小导致假阳性率飙升；
- **最大 64MB**：避免极大数据集占用过多内存；
- **非 2 的幂**：避免 hash 函数对 2 的幂大小产生周期性碰撞模式。

## 3. Checkpoint 目录结构

用户通过 `--checkpoint-dir=DIR` 指定目录（不要与 `-o` / `-e` 混用同一目录）：

```
DIR/
  state.json                # 元数据与进度（JSON 格式，原子 rename 更新）
  .lock                     # flock 并发锁文件（resume 时创建，结束时删除）
  blobs/
    stringpool              # 进入切片后的 pool 快照（pool 非空时才有）
    geom.initial            # 初始快照（阶段 A 完成后写入，未压缩）
    geom.0.g1               # 第 1 代、slot 0 的 geom 分片（z=iz 完成后写入）
    geom.1.g1               # 第 1 代、slot 1 的 geom 分片
    ...
    geom.{slot}.g{gen}      # 第 gen 代、slot N 的 geom 分片
    shared_nodes            # 启用 shared borders 且 nodepos > 0 时
    shared_nodes.bloom
    pool_off.bin            # 各读入线程在 pool 中的偏移（CPUS 个 long long）
    initial_x.bin           # 各读入线程的初始 x 坐标（CPUS 个 unsigned）
    initial_y.bin           # 各读入线程的初始 y 坐标（CPUS 个 unsigned）
    layermaps.bin           # 图层快照（v3 格式，含 tilestats）
    skip_children.bin       # 每个 zoom 提交后更新（不存在时视为空集合）
    strategies.bin          # 每个 zoom 提交后更新（不存在时视为空集合）
    file_bbox.bin           # 数据全局 bbox（z=32 像素坐标，4 个 long long）
    file_bbox1.bin          # -180~180 世界面 bbox（4 个 long long）
    file_bbox2.bin          # 0~360 世界面 bbox（4 个 long long）
  staging/                  # 写入临时文件，提交后 rename 到 blobs/
  commits/                  # zoom 完成标记文件（防御性校验）
    zoom-0.done             # zoom 0 完成标记
    zoom-1.done             # zoom 1 完成标记
    ...
```

**geom 文件命名规则**：

- `geom.initial`：阶段 A 完成后的初始快照，未压缩，仅 1 个文件（slot 0）；
- `geom.{slot}.g{gen}`：每个 zoom 完成后写入，压缩格式，`slot` 范围 `0..TEMP_FILES-1`，`gen` 递增；
- 当 `last_completed_zoom < 0`（无 zoom 完成）时，resume 加载 `geom.initial`；
- 当 `last_completed_zoom >= 0` 时，resume 加载 `state_.generation` 对应的所有 `geom.{slot}.g{gen}`，并清理 `geom.initial` 和旧代数文件。

## 4. 命令行参数

### 4.1 参数一览

| 参数 | 等价形式 | 说明 |
|------|----------|------|
| `--checkpoint-dir=DIR` | `--checkpoint-dir DIR` | 启用 checkpoint，元数据与 blobs 写入 `DIR` |
| `--resume=DIR` | `--resume DIR` | 从已有 checkpoint 目录续跑；**自包含**，无需其他参数 |
| `--checkpoint-force` | — | 若 `DIR` 中已有作业，清空后重新开始（仅影响 checkpoint 目录，不是 `-f`） |
| `--checkpoint-status=DIR` | — | 查询 checkpoint 状态（不启动 resume），打印到 stderr 后退出 |
| `--checkpoint-prune=DIR` | — | 清理 checkpoint 目录中的 `blobs/`、`staging/`、`commits/`，保留 `state.json` 作为日志 |

### 4.2 自包含 resume 行为

`--resume=DIR` 是 **自包含的**：所有续跑所需的信息都从 checkpoint 目录的 `state.json` 读取，命令行无需（也不应该）传入 `-o`、`-e`、`-z`、`-Z`、`-F`、输入文件等参数。

| 命令行参数 | resume 时的处理 |
|------------|-----------------|
| `-o out.mbtiles` | 打印 `note: ignoring -o/-e with --resume (using stored output path)`，忽略；使用 checkpoint 中存储的 `output_path` |
| `-e outdir` | 同上 |
| `-z` / `-Z` / `-d` / `-q` 等 | 忽略；使用 checkpoint 中存储的 `maxzoom` / `minzoom` |
| 输入文件路径 | 忽略；使用 checkpoint 中 `input_files` 存储的路径列表 |
| `-F` / `--allow-existing` | 自动等价启用（`forcetable = 1`），无需手动传入 |
| `-f` / `--force` | 打印 `warning: ignoring -f with --resume (tiles must be preserved)`，忽略；resume 必须保留已写入的瓦片 |

### 4.3 管理命令

#### `--checkpoint-status=DIR`

查询 checkpoint 状态，不启动 resume，不获取锁。输出示例：

```
=== Checkpoint: /data/job-42 ===
  Command: tippecanoe -z14 -o /data/out.mbtiles /data/in.geojson
  Output: /data/out.mbtiles (mbtiles)
  Input: /data/in.geojson
  Zoom range: 0-14, completed: 8/15 (53%)
  Entry snapshot: done
  Generation: 8
  Zoom commits: 8
  Blob size: 52428800 bytes (50.0 MB)
  Created: Mon Jul 15 10:00:00 2026
  Updated: Mon Jul 15 10:30:00 2026
```

#### `--checkpoint-prune=DIR`

清理 checkpoint 目录中的 blob 数据（`blobs/`、`staging/`、`commits/`、`.lock`），保留 `state.json` 作为日志。适用于 checkpoint 已完成且不再需要 resume、想回收磁盘空间的场景。

```

  state.json preserved as log
```

**注意**：prune 后该 checkpoint **无法再 resume**（blobs 已删除）。仅保留 state.json 供 `--checkpoint-status` 查看历史。

| 场景 | 命令 |
|------|------|

## 5. 使用教程

### 5.1 首次运行（启用 checkpoint）

```bash
tippecanoe -z14 -Z0 \
  -o /data/out.mbtiles \
  --checkpoint-dir=/data/job-42 \
  /data/in.geojson
```

说明：

- checkpoint 目录可以事先不存在，会自动创建（含 `blobs/`、`staging/`、`commits/` 子目录）；
- 若目录里 **已有** 未清除的作业（存在 `state.json`），需加 `--checkpoint-force` 或换目录。

### 5.2 中断后续跑（自包含 resume）

```bash
# 只需一个参数：--resume 指向 checkpoint 目录
tippecanoe --resume=/data/job-42
```

程序会自动：

1. 获取 `flock` 并发锁（防止多进程同时 resume）；
2. 从 `state.json` 读取原始命令、输出路径、zoom 范围、输入文件列表；
3. 打印 resume 摘要（原始命令、输出路径、输入文件、zoom 范围、续跑起始 zoom）；
4. 忽略命令行上的 `-o` / `-e` / `-z` / `-Z` / `-f` 等参数（如有）；
5. 自动设置 `forcetable = 1`（等价于 `-F`）；
6. 清理 kill -9 残留（WAL/SHM/JOURNAL、未提交 zoom 的瓦片/目录）；
7. 校验 checkpoint 内部一致性（fingerprint）；
8. 从 `last_completed_zoom + 1` 继续切片；
9. 完成后重建 metadata（`bounds` / `center` / `vector_layers` / `tilestats` 等，与正常路径完全一致）。

**resume 摘要输出示例**：

```
=== Resuming from checkpoint: /data/job-42 ===
  Original command: tippecanoe -z14 -Z0 -o /data/out.mbtiles --checkpoint-dir=/data/job-42 /data/in.geojson
  Output: /data/out.mbtiles (mbtiles)
  Input: /data/in.geojson
  Zoom range: 0-14
  Resuming from zoom 8 (last completed: 7)
========================================
```

### 5.3 SIGTERM 优雅退出

向正在运行的 tippecanoe 发送 `SIGTERM` 或 `SIGINT`（Ctrl+C）：

```bash
tippecanoe -z14 -o /data/out.mbtiles --checkpoint-dir=/data/job-42 /data/in.geojson &
PID=$!

# 发送 SIGTERM
kill -TERM $PID
wait $PID
```

程序行为：

1. 信号处理器设置 `g_shutdown_requested = 1`；
2. 当前 zoom 的切片和 checkpoint 提交 **正常完成**；
3. 在下一个 zoom 开始前检测到 `shutdown_requested()`，打印 `Shutdown signal received; stopping after zoom N.`；
4. 退出码为 `EXIT_INCOMPLETE`（100）；
5. checkpoint 状态已保存，可直接 `--resume` 继续：

```bash
tippecanoe --resume=/data/job-42
```

### 5.4 kill -9 后的自动清理

进程被 `kill -9` 后，resume 会 **自动** 执行以下清理（无需手动干预）：

#### 5.4.1 mbtiles 模式

1. **`cleanup_resume_wal(output_path)`**（在打开输出 DB 之前调用）：
   - 删除 `*-wal`、`*-shm` 文件；
   - 重置 DB header 的 WAL magic 为 DELETE 模式；
   - `sqlite3_open` + `PRAGMA journal_mode=DELETE` 回滚热日志中的未完成事务；
   - 删除 `*-journal` 文件。

2. **`cleanup_resume_tiles(outdb, last_completed_zoom)`**（在打开输出 DB 之后调用）：
   - `DELETE FROM map WHERE zoom_level > last_completed_zoom`（删除未提交 zoom 的瓦片）；
   - `DELETE FROM images WHERE tile_id NOT IN (SELECT tile_id FROM map)`（删除孤立 images）。

#### 5.4.2 目录模式

**`cleanup_resume_dirs(output_path, last_completed_zoom, maxzoom)`**：
- 对 `z = last_completed_zoom + 1 .. maxzoom`，使用 `rmrf_path`（C 递归删除）删除对应 zoom 目录。

### 5.5 查询 checkpoint 状态

```bash
tippecanoe --checkpoint-status=/data/job-42
```

无需启动 resume，仅读取 `state.json` 并打印进度、blob 大小、创建/更新时间等。

### 5.6 清理 checkpoint blobs

```bash
tippecanoe --checkpoint-prune=/data/job-42
```

删除 `blobs/`、`staging/`、`commits/`、`.lock`，保留 `state.json` 作为历史日志。**prune 后无法再 resume**。

### 5.7 清空 checkpoint 后重新开作业

```bash
tippecanoe --checkpoint-dir=/data/job-42 --checkpoint-force \
  -o /data/out.mbtiles -f \
  /data/in.geojson
```

- `-f`：删除或覆盖 **输出** mbtiles；
- `--checkpoint-force`：清空 **checkpoint 目录** 内旧作业（`rmrf_path` 删除 `blobs/` 和 `staging/` 内容，删除 `state.json`）。

### 5.8 目录输出示例

```bash
# 首次运行
tippecanoe -z10 -e /data/tiles \
  --checkpoint-dir=/data/job-tiles \
  china.geojson

# 续跑（自包含）
tippecanoe --resume=/data/job-tiles
```

### 5.9 投影（CRS）提示

若 GeoJSON 内声明的 CRS 与 tippecanoe 默认不一致（例如 EPSG:4490），日志会有警告。这不影响 checkpoint 机制本身；若需指定投影，加上 `-s` 等参数。由于 resume 是自包含的，首次与续跑的投影参数自然一致（都从 checkpoint 读取）。

## 7. 行为与退出码

| 情况 | 行为 |
|------|------|
| 切片未跑完所有 zoom | 与原先一致，可能返回 `100`（`EXIT_INCOMPLETE`）；checkpoint 中记录 `last_completed_zoom`，续跑从下一级补 |
| 收到 SIGTERM/SIGINT | 完成当前 zoom 后优雅退出，返回 `100`（`EXIT_INCOMPLETE`）；checkpoint 已保存 |
| checkpoint 状态不一致（fingerprint 不匹配） | 退出 `101`（`EXIT_ARGS`），打印 stored / expected 指纹 |
| `--resume` 但 checkpoint 无 entry snapshot | 退出 `101`（`EXIT_ARGS`），提示「initial snapshot not saved, please re-run from scratch」 |
| 同时指定 `--checkpoint-dir` 与 `--resume` | 退出 `101`（`EXIT_ARGS`），提示两者不能同时使用 |
| checkpoint 目录已有作业但未加 `--checkpoint-force` | 退出 `104`（`EXIT_EXISTS`），提示使用 `--checkpoint-force` |
| checkpoint 被其他进程锁定（flock） | 退出 `104`（`EXIT_EXISTS`），提示「checkpoint is locked by another process」 |
| PMTiles 输出 + `--resume` | 退出 `101`（`EXIT_ARGS`），提示改用 mbtiles 或目录 |
| 读入阶段中断且无 entry snapshot | `--resume` 退出 `101`，提示从 scratch 重跑 |
| `--resume` 时命令行有 `-o` / `-e` | 打印 `note: ignoring -o/-e`，使用存储的 output_path |
| `--resume` 时命令行有 `-f` | 打印 `warning: ignoring -f`，强制保留已写入瓦片 |
| `--resume` 时无输入文件参数 | 自动从 `input_files` 读取输入文件列表 |
| kill -9 后 `--resume` | 自动清理 WAL/SHM/JOURNAL、回滚热日志、删除未提交 zoom 的瓦片/目录 |
| `--checkpoint-status` | 不获取锁，仅读取 state.json 打印状态后退出 |
| `--checkpoint-prune` | 删除 blobs/ 等，保留 state.json；prune 后无法再 resume |
| **v3**：blob CRC32 校验失败 | 退出 `121`（`EXIT_CHECKPOINT`），提示「checkpoint data may be corrupted. Please re-run from scratch without --resume」 |
| **v3**：磁盘空间不足（`statfs` 预检） | 退出 `121`（`EXIT_CHECKPOINT`），打印所需空间与可用空间，提示 abort |

## 8. 故障排查

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| `checkpoint fingerprint mismatch` | checkpoint 状态被外部篡改或损坏 | 检查 `state.json` 是否被手动修改；若损坏严重，用 `--checkpoint-force` 从 scratch 重跑 |
| `checkpoint directory already has a job` | 目录里已有作业 | `--checkpoint-force` 或换新 `--checkpoint-dir` |
| `checkpoint is locked by another process` | 另一个进程正在 resume 同一 checkpoint | 等待另一进程完成，或手动删除 `.lock` 文件（仅在确认无其他进程时） |
| `checkpoint is incomplete (initial snapshot not saved)` | 进程在读入阶段被 kill，未进入切片阶段 | 从 scratch 重跑（不加 `--resume`） |
| `--resume is not supported for PMTiles` | 输出为 PMTiles | 改用 mbtiles 或 `-e` 目录 |
| `wrong length decoding feature` | blobs/ 中存在过期 geom 数据 | 确保使用最新代码（已修复 geom 原子替换逻辑） |
| `database is locked` (exit 116) | kill -9 后热日志未回滚 | 已在 `cleanup_resume_wal` 中自动处理；若仍出现，确保使用最新代码 |
| `UNIQUE constraint failed` | resume 时 mbtiles 中有未提交 zoom 的瓦片 | 已在 `cleanup_resume_tiles` 中自动处理；若仍出现，手动删除未提交 zoom 的瓦片 |
| 续跑很快结束、瓦片未增加 | 首次已跑完全部 zoom | 正常；检查 `last_completed_zoom` 是否已达 `maxzoom` |
| resume 后输出 0 个瓦片 | 旧版本 `copy_fd_to_file` 的 fd 偏移量 bug | 确保使用已修复该 bug 的版本 |
| resume 后 metadata.bounds 不正确 | 旧版本未持久化 `file_bbox` | 确保使用已修复该问题的版本（v3 layermaps + file_bbox.bin） |
| resume 后 vector_layers / tilestats 为空 | 旧版本 layermaps 格式（v1/v2）不含 tilestats | 确保使用 v3 格式；旧 checkpoint 需从 scratch 重跑 |
| **v3**：`checkpoint blob ... CRC32 mismatch` | 磁盘静默错误（bit rot、坏扇区）导致 blob 数据损坏 | 不要继续 resume；用 `--checkpoint-force` 从 scratch 重跑（输入文件未损坏时只需重读一次） |
| **v3**：`checkpoint disk space insufficient` | checkpoint 目录所在文件系统剩余空间不足 | 清理磁盘空间后重跑；或将 `--checkpoint-dir` 指向空间充足的文件系统 |
| **v3**：`checkpoint mmap blob ... CRC32 mismatch` | mmap 区域的 blob 数据损坏 | 同上，从 scratch 重跑 |

查看进度示例：

```bash
# 查看 checkpoint 状态（推荐方式）

# 直接查看 state.json（人类可读）
cat /data/job-42/state.json | python3 -m json.tool

# 查看最后完成的 zoom
grep -o '"last_completed_zoom":[0-9-]*' /data/job-42/state.json

# 查看各 zoom 提交记录数
grep -o '"zoom_commits":{[^}]*}' /data/job-42/state.json
```

## 9. 注意事项与限制条件

### 9.1 当前限制

- 仅 **原生** `main.cpp` / `tile.cpp` 路径，不含 `tippecanoe-db`；
- **读入过程**无增量 checkpoint（阶段 A 中断需全量重跑）；
- checkpoint 磁盘占用约为 **stringpool + geom 分片** 量级，请把 `--checkpoint-dir` 放在空间充足的磁盘；
- **PMTiles 不支持 resume**：PMTiles 格式的追加写入机制与 checkpoint 不兼容；
- `--resume` 时命令行传入的 `-z`、`-Z`、`-d`、`-q`、输入文件等参数均被忽略（使用 checkpoint 中存储的值）；
- 旧版本（v1/v2）的 `layermaps.bin` 与 v3 不兼容，resume 后 `vector_layers` / `tilestats` 会为空（瓦片内容不受影响）；
- `--checkpoint-prune` 后无法再 resume（blobs 已删除，仅保留 state.json 日志）。

### 9.2 安全性保证

- **原子提交**：`on_zoom_complete` 使用 staging → rename → state.json 原子 rename 的提交顺序，保证 `kill -9` 后 `blobs/` 和 `state.json` 中始终存在有效的完整版本；
- **state.json 原子更新**：`state.json.tmp` → `fsync` → `rename` → `fsync dir`，确保 state.json 要么是旧状态要么是新状态，不会出现半截 JSON；
- **flock 并发锁**：防止多进程同时 resume 同一 checkpoint 目录；
- **fd 偏移量保护**：`copy_fd_to_file` 保存并恢复传入 fd 的偏移量，不影响后续读取；
- **容错读取**：`skip_children.bin` 和 `strategies.bin` 不存在时视为空集合，而非报错退出；
- **内部一致性校验**：SHA-256 指纹确保 checkpoint 状态未被外部篡改或损坏；
- **C 递归删除**：`rmrf_path` 替代 `system("rm -rf")`，消除命令注入风险；
- **自动清理**：resume 时自动清理 kill -9 残留（WAL/SHM/JOURNAL、未提交瓦片、未提交目录），无需手动干预；
- **热日志回滚**：`cleanup_resume_wal` 先让 SQLite 回滚热日志，再删除 journal 文件，确保 mbtiles 输出数据库一致性；
- **metadata 一致性**：`file_bbox` 持久化 + `layermaps` v3 确保 resume 后的 `bounds` / `center` / `vector_layers` / `tilestats` 与正常路径完全一致；
- **SIGTERM 优雅退出**：收到信号后完成当前 zoom 再退出，checkpoint 状态已保存。

### 9.3 已修复的历史问题

| 问题 | 原因 | 修复方式 |
|------|------|----------|
| resume 后 `metadata.bounds` 不正确 | resume 路径未恢复 `file_bbox`，使用默认值计算 bounds | 持久化 `file_bbox.bin` / `file_bbox1.bin` / `file_bbox2.bin`，resume 时恢复并重建 bbox |
| resume 后 `vector_layers` / `tilestats` 为空 | `layermaps.bin` v1/v2 格式不含 `description` 和 `tilestats` 字段 | 升级到 v3 格式，序列化完整的 `layermap_entry` |
| `database is locked` (exit 116) | `cleanup_resume_wal` 先删除 `-journal` 文件，导致 SQLite 无法回滚热日志 | 调整顺序：先删 WAL/SHM → 重置 DB header → sqlite3_open 回滚热日志 → 最后删 journal |
| `make checkpoint-test` 失败 | 旧测试用例与自包含 resume 行为不匹配；瓦片数期望值错误 | 重写 `checkpoint-test` 目标，测试自包含 resume + metadata diff + kill -9 自动清理 + SIGTERM + prune |
| SQLite WAL 崩溃窗口 | v1 使用 SQLite 存储状态，WAL/Journal 有崩溃恢复窗口 | v2 改用纯文件系统方案（state.json + 原子 rename），消除 SQLite 状态依赖 |
| `system("rm -rf")` 命令注入 | 使用 `system()` 调用 shell 删除目录，存在注入风险 | 改用 C 递归删除 `rmrf_path` |
| **v3**：磁盘静默错误导致续跑产生损坏瓦片 | v2 blob 文件无校验，bit rot / 坏扇区无法检测 | v3 为所有 blob 追加 CRC32，restore 时校验完整性 |
| **v3**：磁盘空间不足导致 ENOSPC 中断 | v2 写到一半才报空间不足，可能留下半截状态 | v3 在 `snapshot_tiling_entry` / `on_zoom_complete` 前 `statfs` 预检 |
| **v3**：世代清理 O(n) 目录扫描开销 | v2 每次清理需 `opendir` + `readdir` 遍历整个 `blobs/` | v3 增加 `current_gen_files` 索引，O(1) unlink |
| **v3**：bloom filter 大小固定不合理 | v2 对小数据集浪费内存，对大数据集假阳性率过高 | v3 自适应大小（1MB ~ 64MB），基于 `nodepos` 估算 |
| **v3**：`fsync` 目录阻塞主线程 | v2 同步 fsync 目录元数据，慢盘上延迟数百毫秒 | v3 异步 fsync（detached thread） |
| **v3**：mtime/size 碰撞导致错误 resume | v2 指纹仅含 mtime + size，文件被原地替换但巧合相同则误判 | v3 对 < 100MB 文件计算 SHA-256 content_hash 纳入指纹 |
| 无并发保护 | v1 无锁，多进程可同时 resume | v2 添加 `flock(LOCK_EX\|LOCK_NB)` 并发锁 |
| 无优雅退出 | v1 收到 SIGTERM 直接退出，可能丢失当前 zoom 进度 | v2 添加 SIGTERM/SIGINT 信号处理，zoom 边界检查后优雅退出 |

### 9.4 后续可能增加

- 读入阶段按文件/块增量 checkpoint（详见 [文件读取阶段断点续传设计方案.md](./文件读取阶段断点续传设计方案.md)）；
- PMTiles 可续写或完成后一键转换；
- `tippecanoe-db` 共用 checkpoint 库；
- **v3 后续候选**：
  - blob 文件级 SHA-256 完整校验（当前仅 CRC32，速度优先）；
  - 跨机器 checkpoint 迁移（序列化绝对路径为相对路径）；
  - 多输入文件并行 checkpoint（当前为整体 checkpoint）；
  - 实时磁盘空间监控（当前仅在 zoom 边界检查）。
