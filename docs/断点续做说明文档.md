# Tippecanoe 断点续做（Checkpoint / Resume）

> **架构版本**：v3.3（`format_version=3`），代码版本 v2.80.0
>
> 本文描述原生 `tippecanoe`（GeoJSON / CSV / FlatGeobuf 等读入路径）的 **zoom 级断点续做** 功能。不包含 `tippecanoe-db`（PostGIS / Mongo 等）。
>
> 续跑时只需 `--resume=DIR` 一个参数，所有必要的输出路径、zoom 范围、输入文件列表均从 checkpoint 目录自动恢复，无需在命令行重复传入。

---

## 1. 功能概述

在生成矢量瓦片时，任务往往耗时很长。进程被 `kill -9`、OOM 或机器重启打断后，传统做法只能从头重跑。断点续做提供：

- **专用 checkpoint 工作目录**（与 `-o` / `-e` 输出路径分开）；
- **每个 zoom 成功结束后** 落盘中间状态；
- **自包含 `--resume=DIR`**：跳过读入与 radix，从上一完成 zoom 的下一级继续切片；
- **自动清理 kill -9 残留**：WAL/SHM/JOURNAL 文件、未提交 zoom 的瓦片和目录；
- **自动恢复 metadata**：`bounds` / `center` / `antimeridian_adjusted_bounds` / `vector_layers` / `tilestats` 与正常路径完全一致；
- **SIGTERM/SIGINT 优雅退出**：收到信号后完成当前 zoom 再退出；
- **flock 并发锁**：防止多个进程同时 resume 同一 checkpoint；
- **进度报告**：每个 zoom 完成后打印百分比和预估剩余时间；
- **管理命令**：`--checkpoint-status=DIR` 查询状态，`--checkpoint-prune=DIR` 清理 blobs；
- **CRC32 数据完整性校验**：blob 文件末尾追加 CRC32，resume 时自动校验，防止磁盘静默错误；
- **磁盘空间预算检查**：写入前预检 `statfs`，空间不足立即以退出码 121 退出；
- **断电一致性保证**：所有 blob 文件在 `fclose` 前 `fsync`；`save_state_atomic` 内部先等待 blobs fsync 完成；启动时 `verify_blobs_consistency` 检查 blobs 完整性。

### 1.1 两阶段模型

| 阶段 | 内容 | 是否 checkpoint |
|------|------|-----------------|
| **阶段 A** | 读入 GeoJSON、radix 排序、合并 stringpool、建 shared_nodes 等 | **否** |
| **阶段 B** | `traverse_zooms`：按 zoom 写 mbtiles 或目录瓦片 | **是**（每 zoom 一次） |

因此：

- 中断发生在 **读入 / 排序** 时：checkpoint 目录里通常没有可用的切片入口快照，下次只能 **全量重跑**。
- 中断发生在 **切片过程中**：已完成的 zoom 有记录，可 **`--resume` 续跑**。

「zoom 级」不是「只记录 mbtiles 里已有哪些 z」，而是必须保存 **算法中间态**（否则无法从 z+1 继续，因为 z+1 的输入来自 z 结束时生成的 geom 分片，且属性索引依赖同一次读入的 stringpool）。

## 2. 设计原理

### 2.1 核心架构：纯文件系统 + 原子 rename

| 内容 | 存储位置 | 原因 |
|------|----------|------|
| 作业指纹、命令行、zoom 进度、时间戳 | `state.json` | 纯文本 JSON，原子 rename 更新，无 SQLite 依赖 |
| stringpool、geom 分片、shared_nodes、bloom、file_bbox | `blobs/` 下普通文件 | 可达 GB 级；使用 `mmap` 直接映射 |
| 写入中的数据 | `staging/` | 写完后 `rename` 到 `blobs/`，再更新 state.json |
| 并发锁 | `.lock` 文件 + `flock` | 防止多进程同时 resume |
| zoom 完成标记 | `commits/zoom-N.done` | 防御性校验，证明 zoom 已提交 |

核心思想：

- **state.json 原子更新**：先写 `state.json.tmp`，`fflush` + `fsync` + `fclose`，然后 `rename` 覆盖 `state.json`，再 `fsync` 目录。`rename()` 在同一文件系统上是原子操作，保证 `kill -9` 后 state.json 始终是完整的旧版本或完整的新版本；
- **无 SQLite 状态依赖**：消除了 SQLite WAL/Journal 的崩溃恢复窗口。SQLite 仅用于 mbtiles **输出格式** 的 WAL 清理。

### 2.2 原子提交顺序

每个 zoom 的 commit 顺序为：

1. 将新的 geom 分片、`skip_children`、`strategies` 写入 `staging/`；
2. 对相关文件 `fsync`；
3. **原子 `rename`** `staging/` → `blobs/`（有新数据的文件原子替换旧版本，无新数据的 slot 不写文件）；
4. 清理旧代数的 geom 文件；
5. **`fsync` blobs/ 目录**；
6. **原子更新 state.json**（`save_state_atomic`：内部先 `wait_pending_fsync()`，再写 `state.json.tmp` → `fsync` → `rename` → `fsync dir`）；
7. 创建 `commits/zoom-N.done` 标记文件；
8. `report_progress(z)`。

**关键**：步骤 3 中直接 `rename` 覆盖（不先删后写），保证 `blobs/` 中始终存在有效版本。步骤 6 的 `wait_pending_fsync()` 确保 blobs fsync 在 state.json 持久化之前完成，保证断电后 state.json 与 blobs 一致。

### 2.3 文件代数（generation）机制

geom 分片文件使用代数后缀命名，避免 rename 覆盖旧文件时的竞态：

| 文件名 | 含义 |
|--------|------|
| `geom.initial` | 初始快照（阶段 A 完成后写入一次，未压缩） |
| `geom.{slot}.g{gen}` | 第 `gen` 代、第 `slot` 个分片（每个 zoom 完成后写入，压缩格式） |

- `slot` 范围：`0 .. TEMP_FILES-1`；
- `gen` 是递增计数器，每次 `on_zoom_complete` 时 `+1`；
- `state.json` 的 `current_gen_files` 字段记录当前 generation 的文件列表，使旧代数清理从 O(n) 目录扫描降为 O(1) 直接 unlink。若 `current_gen_files` 为空则自动回退到 `opendir` 扫描。

### 2.4 并发锁（flock）

```
acquire_lock():
  1. 创建 {dir}/.lock 文件
  2. flock(lock_fd, LOCK_EX | LOCK_NB)
     ├── 成功 → 获得锁，继续
     └── 失败 → exit(EXIT_EXISTS)

release_lock():
  flock(lock_fd, LOCK_UN) → close → unlink(.lock)
```

锁是 **建议性锁**（advisory lock），`LOCK_NB`（非阻塞）确保获取不到锁时立即退出而非死等。

### 2.5 SIGTERM/SIGINT 优雅退出

注册信号处理器设置 `g_shutdown_requested = 1`。在 `traverse_zooms` 的 zoom 循环中，每个 zoom 完成后检查：

- 收到 SIGTERM/SIGINT 后，**不会立即退出**，而是完成当前 zoom 的切片和 checkpoint 提交后在下一个 zoom 开始前退出；
- checkpoint 状态已保存，下次 `--resume` 可从断点继续；
- 退出码为 `EXIT_INCOMPLETE`（100）；
- SIGKILL（kill -9）无法被捕获，仍需依赖 checkpoint 的崩溃一致性。

### 2.6 作业指纹（fingerprint）

指纹是一个 **SHA-256 哈希值**，用于校验 checkpoint 状态的 **内部一致性**（不校验 resume 命令行参数）。

`verify_fingerprint_internal()` 从 `state_` 中读取 `normalized_cmd`、`output_mode`、`output_path`、`temp_files`、`cpus`、输入文件信息等存储值重新计算指纹，与 `state_.fingerprint` 比较，确保 checkpoint 状态未被外部篡改或损坏。

**参与哈希的内容**：

- 格式版本 `TIPPECANOE_CHECKPOINT_FORMAT`（当前为 `3`）；
- 规范化后的命令行（已剔除 `--checkpoint-dir`、`--resume`、`--checkpoint-force`、`--checkpoint-status`、`--checkpoint-prune`、`-F`、`-f` 等）；
- 输出模式与输出路径绝对路径；
- `TEMP_FILES`、`CPUS`；
- `prevent[]` / `additional[]` 标志位；
- 输入文件列表：绝对路径 + size + mtime（排序后）；
- 对 < 100MB 的输入文件，额外计算 SHA-256 `content_hash` 纳入指纹，防止 mtime/size 碰撞。大文件不计算内容哈希以避免 I/O 开销。

指纹不匹配会以退出码 `101`（`EXIT_ARGS`）失败。

### 2.7 数据完整性保证

#### CRC32 校验

所有 blob 文件末尾追加 **IEEE 802.3 CRC32**（4 字节），用于检测磁盘静默错误：

- **写入**：`write_blob_file_with_crc()` 在数据末尾追加 4 字节小端 CRC32，然后 `fflush` + `fsync(fileno(fp))` + `fclose`；
- **校验**：`read_blob_with_crc()` 读取整个文件校验末尾 CRC32，返回去掉 CRC 的 data 部分；`verify_mmap_crc()` 对 mmap 区域直接校验（用于 stringpool、shared_nodes、geom 等大文件）；
- **mmap 兼容**：映射整个文件（含 CRC），data 长度减 4，校验末尾 4 字节 CRC；
- **向后兼容**：`blob_has_crc()` 检查 `state_.format_version >= 3`，v2 checkpoint 不校验 CRC。

#### 断电一致性

v3.1 通过以下四项修复保证断电后 checkpoint 的安全性：

1. **`write_blob_file_with_crc` 加 fsync**：在 `fclose` 前增加 `fflush(fp)` + `fsync(fileno(fp))`，保证小 blob 文件（`pool_off.bin` / `initial_x.bin` / `layermaps.bin` / `shared_nodes.bloom` / `file_bbox*.bin`）内容断电后不丢失；
2. **异步 fsync 改用 `std::future`**：`async_fsync_blob_dir` 从 `std::thread + detach` 改为 `std::async + std::future`，析构时和 `save_state_atomic` 之前都会 `wait`，保证进程退出前 fsync 完成；
3. **state.json 与 blobs 严格 ordering**：`save_state_atomic` 内部首先调用 `wait_pending_fsync()`，确保 blobs fsync 在 state.json 持久化之前完成。修复后的时序：
   ```
   T1: copy_fd_to_file + fsync          ← 文件内容已落盘
   T2: write_blob_with_crc + fsync      ← 小文件内容已落盘
   T3: rename(staging → blobs)          ← 目录条目更新
   T4: async_fsync_blob_dir() 启动       ← 异步开始
   T5: save_state_atomic() → wait T4    ← 等 blobs fsync 完成
   T6: fsync state.json.tmp + rename    ← state.json 已落盘
   ```
   关键不变量：T6 完成时，T1~T4 全部已完成并落盘；
4. **`verify_blobs_consistency` 启动检查**：`open_resume` 时检查 `state.json` 中 `current_gen_files` 列出的文件和 entry 必备文件（`layermaps.bin` / `pool_off.bin` / `initial_x.bin` / `initial_y.bin` / `file_bbox.bin`）是否都存在于 `blobs/`。若缺失，说明上次运行断电导致不一致，以 `EXIT_CHECKPOINT=121` 退出。

#### 磁盘空间预算检查

在两处关键写入点前调用 `check_disk_space(required_bytes)`：

1. **`snapshot_tiling_entry`**：估算 `pool_size + geom_size + nodepos + bloom_size + 64MB`；
2. **`on_zoom_complete`**：估算 `sum(geom_size[j]) + 32MB`。

使用 `statfs` / `statvfs` 获取文件系统剩余空间（`f_bavail`），检查失败时以 `EXIT_CHECKPOINT=121` 退出。

### 2.8 其他关键设计

#### `copy_fd_to_file` — fd 到文件的安全拷贝

拷贝 `geomfd[j]` 内容到 blob 文件时，保存并恢复文件偏移量（`lseek`），不影响后续 `fdopen()` 读取。Linux 优先使用 `sendfile()` 零拷贝，其他平台回退到 `read` + `write` 循环（1MB 缓冲区）。拷贝完成后 `fsync` 目标文件。

#### `compressed` 标志

`compressed` 标志决定 `run_thread` 读取 geomfd 时是否走 zlib 解压分支。其规则与数据来源有关：

- **正常启动**：数据从初始读入池（iz zoom）开始，该层数据是**未压缩**的（排序和 fixup 需要）；更高 zoom 的数据是上一轮写出的**压缩**格式。因此 `compressed = (z != iz)`。
- **Resume 启动**：`iz = last_completed_zoom + 1`，该层数据是上一轮写出的**压缩**格式，因此起始 zoom 也应 `compressed = true`。

v3.3 新增 `initial_compressed` 参数来区分上述两种场景：

```cpp
args[thread].compressed = (z != iz) || initial_compressed;
```

| 场景 | iz | 起始 zoom 数据 | initial_compressed | 结果 |
|------|----|----|----|----|
| 正常启动 | 原始 iz（如 4） | 未压缩 | false | `(z != iz)` —— 与上游一致 |
| resume（有已完成 zoom） | last_completed+1 | 压缩 | true | 恒 true |
| resume（无已完成 zoom） | 原始 iz | 未压缩 | false | `(z != iz)` |

> **注意**：早期版本错误地将 `compressed` 改为 `(z != minzoom)`，导致 `iz < minzoom` 时把起始 zoom 的未压缩数据当作压缩流解压，触发 `decompression error -3`。v3.3 已修复此回归。

#### `skip_children` / `strategies` 容错读取

文件不存在时优雅返回空集合（而非报错退出），因为进程在第一个 zoom 完成前被 kill 时 `blobs/` 中尚无这两个文件，但 resume 仍应可以继续。

#### `file_bbox` 持久化与 metadata 重建

| 文件 | 含义 | 默认值 |
|------|------|--------|
| `file_bbox.bin` | 数据全局 bbox（z=32 像素坐标） | `{UINT_MAX, UINT_MAX, 0, 0}` |
| `file_bbox1.bin` | -180~180 世界面 bbox | `{0xFFFFFFFF, 0xFFFFFFFF, 0, 0}` |
| `file_bbox2.bin` | 0~360 世界面 bbox（跨日期线检测） | `{0x1FFFFFFFF, 0xFFFFFFFF, 0x100000000, 0}` |

resume 时读取这三个文件，通过 `tile2lonlat(z=32)` 重建经纬度 bbox，逻辑与正常路径完全一致。

#### `layermaps.bin` 格式

当前使用 v3 格式：包含 `segs`、`layers`（含 `nlen/name/id/minz/maxz`）、`points/lines/polygons/retain`、`description`、完整 `tilestats`（含 `min/max/type/sample_values`）。

若 `layermaps.bin` 版本号不等于 3，会打印警告并返回空 layermaps。瓦片内容不受影响，但 `metadata.vector_layers` 和 `metadata.tilestats` 会为空。

#### 自适应 bloom filter

`shared_nodes_bloom` 大小根据 `nodepos` 动态调整：

```cpp
size_t bloom_size = (nodepos / sizeof(node)) / 2;  // ~8 bits per node, 假阳性率 ~1%
bloom_size = clamp(bloom_size, 1MB, 64MB);
if ((bloom_size & (bloom_size - 1)) == 0) bloom_size += 12345;  // 避免 2 的幂
```

#### `cleanup_resume_wal` 热日志回滚

操作的是 mbtiles **输出文件**（不是 checkpoint 状态）。正确顺序：

1. 删除 WAL/SHM 文件；
2. 重置 DB header（WAL → DELETE 模式）；
3. `sqlite3_open` + `PRAGMA journal_mode=DELETE`（回滚热日志中未完成事务）；
4. 关闭数据库；
5. 删除 `-journal` 文件。

**关键**：步骤 1 中不能先删除 `-journal` 文件，否则 SQLite 无法回滚未完成事务，后续会报 `database is locked`。

#### 进度报告

`on_zoom_complete` 末尾输出：

```
[checkpoint] zoom 11/12 committed (92%), elapsed 2s, est. remaining 0s
```

#### `rmrf_path` 安全删除

替代 `system("rm -rf")`，消除命令注入风险。用于 `clear_workspace()`、`cleanup_resume_dirs()` 和 `checkpoint_prune()`。

## 3. Checkpoint 目录结构

用户通过 `--checkpoint-dir=DIR` 指定目录（不要与 `-o` / `-e` 混用同一目录）：

```
DIR/
  state.json                # 元数据与进度（JSON 格式，原子 rename 更新）
  .lock                     # flock 并发锁文件（resume 时创建，结束时删除）
  blobs/
    stringpool              # 切片后的 pool 快照（pool 非空时才有）
    geom.initial            # 初始快照（阶段 A 完成后写入，未压缩）
    geom.{slot}.g{gen}      # 第 gen 代、slot N 的 geom 分片（压缩格式）
    shared_nodes            # 启用 shared borders 且 nodepos > 0 时
    shared_nodes.bloom
    pool_off.bin            # 各线程在 pool 中的偏移（CPUS × long long）
    initial_x.bin           # 各线程的初始 x 坐标（CPUS × unsigned）
    initial_y.bin           # 各线程的初始 y 坐标（CPUS × unsigned）
    layermaps.bin           # 图层快照（v3 格式，含 tilestats）
    skip_children.bin       # 每个 zoom 提交后更新（不存在时视为空集合）
```

## 4. 命令行参数

### 4.1 参数一览

| 参数 | 等价形式 | 说明 |
|------|----------|------|
| `--checkpoint-dir=DIR` | `--checkpoint-dir DIR` | 启用 checkpoint，元数据与 blobs 写入 `DIR` |
| `--resume=DIR` | `--resume DIR` | 从已有 checkpoint 目录续跑；**自包含**，无需其他参数 |
| `--checkpoint-force` | — | 若 `DIR` 中已有作业，清空后重新开始（仅影响 checkpoint 目录，不是 `-f`） |
| `--checkpoint-status=DIR` | — | 查询 checkpoint 状态（不启动 resume），打印到 stderr 后退出 |
| `--checkpoint-prune=DIR` | — | 清理 `blobs/`、`staging/`、`commits/`，保留 `state.json` 作为日志 |

### 4.2 自包含 resume 行为

`--resume=DIR` 是自包含的：所有续跑所需信息都从 `state.json` 读取。

| 命令行参数 | resume 时的处理 |
|------------|-----------------|
| `-o out.mbtiles` | 打印 `note: ignoring -o/-e with --resume`，忽略 |
| `-e outdir` | 同上 |
| `-z` / `-Z` / `-d` / `-q` 等 | 忽略；使用 checkpoint 中存储的值 |
| 输入文件路径 | 忽略；使用 checkpoint 中 `input_files` 存储的路径列表 |
| `-F` / `--allow-existing` | 自动等价启用（`forcetable = 1`） |
| `-f` / `--force` | 打印 `warning: ignoring -f with --resume`，忽略 |

### 4.3 管理命令

#### `--checkpoint-status=DIR`

查询 checkpoint 状态，不启动 resume，不获取锁。输出示例：

```
=== Checkpoint: /data/job-42 ===
  Command: tippecanoe -z14 -o /data/out.mbtiles /data/in.geojson
  Output: /data/out.mbtiles (mbtiles)
  Input: /data/in.geojson
  Zoom range: 0-14, completed: 8/15 (53%)
  Entry snapshot: done
  Generation: 8
  Zoom commits: 8
  Blob size: 52428800 bytes (50.0 MB)
  Created: Mon Jul 15 10:00:00 2026
  Updated: Mon Jul 15 10:30:00 2026
```

#### `--checkpoint-prune=DIR`

清理 `blobs/`、`staging/`、`commits/`、`.lock`，保留 `state.json`。**prune 后无法再 resume**。

### 4.4 使用场景

| 场景 | 命令 |
|------|------|
| 首次跑 + checkpoint | `tippecanoe -z14 -o out.mbtiles --checkpoint-dir=DIR input.geojson` |
| 续跑（自包含） | `tippecanoe --resume=DIR` |
| 查询状态 | `tippecanoe --checkpoint-status=DIR` |
| 清理 blobs | `tippecanoe --checkpoint-prune=DIR` |
| 清空 checkpoint 重来 | `tippecanoe --checkpoint-dir=DIR --checkpoint-force -o out.mbtiles -f input.geojson` |
| 无 checkpoint 参数 | 行为与未加此功能前完全一致 |

### 4.5 输出格式

| 输出 | 首次 `--checkpoint-dir` | `--resume` |
|------|-------------------------|------------|
| mbtiles（`-o *.mbtiles`） | 支持 | 支持 |
| 目录（`-e DIR`） | 支持 | 支持 |
| PMTiles（`-o *.pmtiles`） | 可记录指纹 | **不支持**，会报错并提示先用 mbtiles/目录，再转 PMTiles |

## 5. 使用教程

### 5.1 首次运行（启用 checkpoint）

```bash
tippecanoe -z14 -Z0 \
  -o /data/out.mbtiles \
  --checkpoint-dir=/data/job-42 \
  /data/in.geojson
```

checkpoint 目录可以事先不存在，会自动创建（含 `blobs/`、`staging/`、`commits/` 子目录）。若目录里已有未清除的作业（存在 `state.json`），需加 `--checkpoint-force` 或换目录。

### 5.2 中断后续跑

```bash
tippecanoe --resume=/data/job-42
```

程序自动：获取 flock → 从 state.json 读取所有参数 → 打印 resume 摘要 → 忽略命令行多余参数 → 清理 kill -9 残留 → 校验指纹 → 从 `last_completed_zoom + 1` 继续切片 → 完成后重建 metadata。

**resume 摘要输出示例**：

```
=== Resuming from checkpoint: /data/job-42 ===
  Original command: tippecanoe -z14 -Z0 -o /data/out.mbtiles --checkpoint-dir=/data/job-42 /data/in.geojson
  Output: /data/out.mbtiles (mbtiles)
  Input: /data/in.geojson
  Zoom range: 0-14
  Resuming from zoom 8 (last completed: 7)
========================================
```

### 5.3 SIGTERM 优雅退出

```bash
tippecanoe -z14 -o /data/out.mbtiles --checkpoint-dir=/data/job-42 /data/in.geojson &
PID=$!
kill -TERM $PID
wait $PID
# 退出码 100，checkpoint 已保存
tippecanoe --resume=/data/job-42
```

### 5.4 kill -9 后的自动清理

resume 时 **自动** 执行以下清理：

**mbtiles 模式**：
1. `cleanup_resume_wal`：删除 WAL/SHM → 重置 DB header → sqlite3_open 回滚热日志 → 删除 journal；
2. `cleanup_resume_tiles`：`DELETE FROM map WHERE zoom_level > last_completed_zoom` → 删除孤立 images。

**目录模式**：
- `cleanup_resume_dirs`：用 `rmrf_path` 删除未提交 zoom 的目录。

### 5.5 管理命令

```bash
# 查询状态
tippecanoe --checkpoint-status=/data/job-42

# 清理 blobs（prune 后无法再 resume）
tippecanoe --checkpoint-prune=/data/job-42
```

### 5.6 清空 checkpoint 后重新开作业

```bash
tippecanoe --checkpoint-dir=/data/job-42 --checkpoint-force \
  -o /data/out.mbtiles -f \
  /data/in.geojson
```

`-f` 删除/覆盖输出 mbtiles；`--checkpoint-force` 清空 checkpoint 目录内旧作业。

### 5.7 目录输出示例

```bash
tippecanoe -z10 -e /data/tiles --checkpoint-dir=/data/job-tiles china.geojson
tippecanoe --resume=/data/job-tiles
```

## 7. 行为与退出码

| 退出码 | 常量 | 含义 | checkpoint 相关场景 |
|--------|------|------|---------------------|
| 0 | — | 成功 | 所有 zoom 完成 |
| 100 | `EXIT_INCOMPLETE` | 瓦片不完整 | 部分 zoom 完成（SIGTERM 退出或数据不足），checkpoint 已记录 |
| 101 | `EXIT_ARGS` | 参数错误 | fingerprint 不匹配、`--checkpoint-dir` 与 `--resume` 同时使用、checkpoint 无 entry snapshot、PMTiles 输出 + `--resume` |
| 104 | `EXIT_EXISTS` | 文件已存在 | checkpoint 目录已有作业但未加 `--checkpoint-force`；checkpoint 被其他进程锁定 |
| 121 | `EXIT_CHECKPOINT` | checkpoint 错误 | blob CRC32 校验失败、磁盘空间不足、blobs 与 state.json 不一致 |

| 情况 | 行为 |
|------|------|
| 收到 SIGTERM/SIGINT | 完成当前 zoom 后优雅退出，返回 100 |
| kill -9 后 `--resume` | 自动清理 WAL/SHM/JOURNAL、回滚热日志、删除未提交 zoom 的瓦片/目录 |
| `--resume` 时命令行有 `-o` / `-e` | 打印 `note: ignoring -o/-e`，使用存储的 output_path |
| `--resume` 时命令行有 `-f` | 打印 `warning: ignoring -f`，强制保留已写入瓦片 |
| `--resume` 时无输入文件参数 | 自动从 `input_files` 读取输入文件列表 |
| 读入阶段中断且无 entry snapshot | `--resume` 退出 101，提示从 scratch 重跑 |
| `--checkpoint-status` | 不获取锁，仅读取 state.json 打印状态后退出 |
| `--checkpoint-prune` | 删除 blobs/ 等，保留 state.json；prune 后无法再 resume |

## 8. 故障排查

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| `checkpoint fingerprint mismatch` | checkpoint 状态被外部篡改或损坏 | 检查 `state.json` 是否被手动修改；若损坏严重，用 `--checkpoint-force` 从 scratch 重跑 |
| `checkpoint directory already has a job` | 目录里已有作业 | `--checkpoint-force` 或换新 `--checkpoint-dir` |
| `checkpoint is locked by another process` | 另一个进程正在 resume | 等待另一进程完成，或手动删除 `.lock` 文件（仅在确认无其他进程时） |
| `checkpoint is incomplete (initial snapshot not saved)` | 进程在读入阶段被 kill | 从 scratch 重跑（不加 `--resume`） |
| `--resume is not supported for PMTiles` | 输出为 PMTiles | 改用 mbtiles 或 `-e` 目录 |
| `database is locked` (exit 116) | kill -9 后热日志未回滚 | 已在 `cleanup_resume_wal` 中自动处理；若仍出现，确保使用最新代码 |
| `UNIQUE constraint failed` | resume 时 mbtiles 中有未提交 zoom 的瓦片 | 已在 `cleanup_resume_tiles` 中自动处理 |
| 续跑很快结束、瓦片未增加 | 首次已跑完全部 zoom | 检查 `last_completed_zoom` 是否已达 `maxzoom` |
| resume 后 metadata.bounds 不正确 | 旧版本未持久化 `file_bbox` | 确保使用已修复该问题的版本 |
| resume 后 vector_layers / tilestats 为空 | layermaps.bin 版本不是 v3 | 旧 checkpoint 需从 scratch 重跑 |
| `checkpoint blob ... CRC32 mismatch` | 磁盘静默错误导致 blob 数据损坏 | 用 `--checkpoint-force` 从 scratch 重跑 |
| `checkpoint disk space insufficient` | 文件系统剩余空间不足 | 清理磁盘空间或将 `--checkpoint-dir` 指向空间充足的文件系统 |
| `checkpoint blobs/ is inconsistent with state.json` | 上次运行断电导致 fsync 未完成 | 用 `--checkpoint-force` 从 scratch 重跑 |

查看进度示例：

```bash
tippecanoe --checkpoint-status=/data/job-42
cat /data/job-42/state.json | python3 -m json.tool
du -sh /data/job-42/blobs/
```

## 9. 注意事项与限制条件

### 9.1 当前限制

- 仅 **原生** `main.cpp` / `tile.cpp` 路径，不含 `tippecanoe-db`；
- **读入过程**无增量 checkpoint（阶段 A 中断需全量重跑）；
- checkpoint 磁盘占用约为 **stringpool + geom 分片** 量级，请把 `--checkpoint-dir` 放在空间充足的磁盘；
- **PMTiles 不支持 resume**；
- `--resume` 时命令行传入的 `-z`、`-Z`、`-d`、`-q`、输入文件等参数均被忽略；
- `--checkpoint-prune` 后无法再 resume；
- 旧版本（v1/v2）的 `layermaps.bin` 与当前格式不兼容，resume 后 `vector_layers` / `tilestats` 会为空（瓦片内容不受影响）。

### 9.2 安全性保证

- **原子提交**：staging → rename → state.json 原子 rename 的提交顺序，保证 `kill -9` 后 `blobs/` 和 `state.json` 中始终存在有效的完整版本；
- **state.json 原子更新**：`state.json.tmp` → `fsync` → `rename` → `fsync dir`，不会出现半截 JSON；
- **断电一致性**：所有 blob 文件在 `fclose` 前 `fsync`；`save_state_atomic` 内部先 `wait_pending_fsync()` 确保严格 ordering；启动时 `verify_blobs_consistency` 检查完整性；
- **flock 并发锁**：防止多进程同时 resume；
- **CRC32 数据校验**：blob 文件追加 CRC32，防止磁盘静默错误导致续跑产生损坏瓦片；
- **磁盘空间预检**：`statfs` 检查剩余空间，不足时以 121 退出；
- **内部一致性校验**：SHA-256 指纹确保 checkpoint 状态未被外部篡改或损坏；
- **fd 偏移量保护**：`copy_fd_to_file` 保存并恢复传入 fd 的偏移量；
- **容错读取**：`skip_children.bin` 和 `strategies.bin` 不存在时视为空集合；
- **C 递归删除**：`rmrf_path` 替代 `system("rm -rf")`，消除命令注入风险；
- **自动清理**：resume 时自动清理 kill -9 残留；
- **热日志回滚**：`cleanup_resume_wal` 先让 SQLite 回滚热日志再删除 journal；
- **metadata 一致性**：`file_bbox` 持久化 + `layermaps` v3 确保 resume 后的 metadata 与正常路径完全一致；
- **SIGTERM 优雅退出**：收到信号后完成当前 zoom 再退出。

### 9.3 后续可能增加

- 读入阶段按文件/块增量 checkpoint；
- PMTiles 可续写或完成后一键转换；
- `tippecanoe-db` 共用 checkpoint 库；
- blob 文件级 SHA-256 完整校验；
- 跨机器 checkpoint 迁移；
- 实时磁盘空间监控。
