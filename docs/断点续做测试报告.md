## 2. 测试方法论

### 2.1 测试分组

测试分为以下 8 组，覆盖正常流程、异常中断、不同任务类型、长时间中断、并发控制、边界条件、管理命令、数据一致性。

| 组 | 名称 | 场景覆盖 |
|----|------|----------|
| M | `make checkpoint-test` | Makefile 内置 8 个场景（含 SIGTERM、kill -9、CRC、断电模拟） |
| A | 多输入格式 | GeoJSON、CSV、多文件 |
| B | 多输出格式 / 多 zoom | mbtiles、directory、pmtiles、不同 zoom 范围 |
| C | 链式中断 | 中断→续做→再中断→再续做→完成 |
| D | 并发锁 | flock 并发锁验证（持锁 + 释放锁） |
| E | 边界条件 | 空 features、单 feature、超多 features |
| F | 管理命令 | `--checkpoint-status`、`--checkpoint-prune` |
| G | 数据一致性 | resume 后瓦片与 baseline 逐字节对比 |

### 2.2 中断模拟方式

- **主动中断**：`kill -9 <pid>`（SIGKILL，模拟 OOM / 进程崩溃）
- **优雅退出**：`kill -TERM <pid>`（SIGTERM，触发 graceful shutdown）
- **断电模拟**：手动删除 blob 文件（模拟 fsync 未完成导致文件丢失）
- **数据损坏模拟**：手动翻转 blob 文件字节（模拟磁盘静默错误）

### 2.3 验证维度

每个测试用例验证以下维度：
1. **退出码**：是否符合预期（0=成功，101=参数错误，121=checkpoint 错误）
2. **state.json 状态**：`last_completed_zoom` 是否正确推进
3. **输出文件完整性**：mbtiles 中 tile 数量、metadata 完整性
4. **瓦片内容**：与 baseline 逐字节对比（仅 G 组）
5. **日志输出**：错误消息是否清晰、resume 信息是否完整

## 4. 发现的缺陷

### 4.1 缺陷 G-1：name/description/attribution 未在 resume 时恢复（v3.2 已修复）

| 项目 | 内容 |
|------|------|
| **严重程度** | 低（不影响瓦片数据，仅影响 metadata 描述字段） |
| **影响范围** | 使用 `-n`、`-N`、`-A` 参数指定 name/description/attribution 时，resume 后这些字段会退化为输出路径或缺失 |
| **根因** | `CheckpointState` 结构体（checkpoint.hpp:70-108）未存储 `name`、`description`、`attribution` 字段；`main.cpp:3952-4025` 的 resume 逻辑也未从 state 恢复这些参数 |
| **修复版本** | v3.2（2026-07-21） |
| **修复方案** | 1. 在 `CheckpointState` 与 `ResumeInfo` 中增加 `name`、`description`、`attribution` 字段<br>2. 在 `FingerprintParams` 中增加这三个字段（不参与指纹计算，仅用于持久化）<br>3. 在 `serialize_state` / `parse_state` 中序列化/反序列化这三个字段<br>4. `open_new` 时从 `FingerprintParams` 拷贝到 `state_`<br>5. `read_resume_info` 时从 `state` 填入 `ResumeInfo`<br>6. `main.cpp` resume 逻辑中用 `strdup(info.name.c_str())` 等覆盖 `name`/`description`/`attribution` 局部变量 |
| **回归测试** | Makefile `checkpoint-test` 场景 9（kill -9 中断 → resume → 验证 mbtiles metadata 与 baseline 一致） |
| **状态** | ✅ 已修复并通过回归测试 |

### 4.2 非缺陷说明

| 项目 | 说明 |
|------|------|
| `generator_options` 差异 | 预期行为：resume 时的命令行与首次运行不同，generator_options 反映实际执行的命令 |
| `name`/`description` 默认为输出路径 | 预期行为：当未指定 `-n`/`-N` 时，tippecanoe 默认使用输出路径作为 name/description。缺陷 G-1 仅在用户**显式指定**了这些参数时才会表现 |
| B3 `decompression error` | tippecanoe 上游几何处理 bug（`-Z2 -z5` 与 `tests/curve/in.json` 的特定组合），与 checkpoint 功能无关 |

## 6. 测试结论

### 6.1 核心功能验证

**断点续做功能在所有核心场景下均能准确、可靠地恢复之前的工作状态**：

1. **瓦片数据零丢失**：在 mbtiles 和 directory 两种输出模式下，4087 个瓦片均与 baseline 逐字节一致
2. **中断恢复可靠**：无论是 `kill -9`（SIGKILL）、SIGTERM 优雅退出、还是模拟断电（blob 删除/CRC 损坏），均能正确检测并恢复
3. **链式中断支持**：支持多次中断→续做的链式操作，每次都能从上一完成 zoom 继续
4. **并发安全**：flock 并发锁有效防止多进程同时 resume
5. **数据完整性校验**：CRC32 校验和 `verify_blobs_consistency` 启动检查能有效检测断电导致的不一致
6. **自包含 resume**：只需 `--resume=DIR` 一个参数，所有输出路径、zoom 范围、输入文件、tileset metadata 均从 checkpoint 自动恢复
