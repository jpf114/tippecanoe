# 05 性能报告

> 2026-10-17 实测，feature/combined @ vendor 化提交（61bc21a），tippecanoe-db 为
> vendor 静态链（libpq 18 + c-driver 1.29.0 + mongocxx r4.0.0，零外部 .so 依赖）。
> 本轮回答的问题："db 效率与 GeoJSON 一致是否合理？是架构限制还是其它原因？"

## 1. 结论

1. **"db 比 GeoJSON 慢 45%" 不成立**（此前观察 2.81s vs 1.94s 无法在当前版本复现，
   推断为当时对比条件错位：不同数据/不同二进制/机器负载）。
2. 小数据下两者持平（db 略快）；**大数据（679 万要素）下 db 快 32%**——
   PG 读取天然并行（4 线程独立连接分批），而 GeoJSON 路径是单线程解析 2.4G 文本。
3. **"效率一致"是正常现象而非测量假象**：两路径在 serialization_state 之后共享同一条
   瓦片管道（v3.4 副本收敛的结构结果），瓦片生成+输出占总耗时的大头，
   读入差异被稀释；数据量放大后读入占比上升，db 的并行优势才显现。
4. **不是架构限制**。文本协议 + hex 传输有约 2x 字节膨胀，但绝对量被并行读吸收，
   在总耗时中占比 ~5%。

## 2. 小数据矩阵（100,000 点，全球，-Z0 -z6，3 次取中位）

| 路径 | 总耗时 | 读入段完成点 | 瓦片数 |
|---|---|---|---|
| GeoJSON（tippecanoe） | 2.40s | - | 5461 |
| DB（tippecanoe-db → mbtiles） | 2.12s | 0.36s（17%） | 5461 |

瓦片数一致（5461 = 5461）；瓦片内容逐字节一致由 china 基准另行验证（见 06）。

## 3. 大数据矩阵（6,789,251 MultiPolygon；GeoJSON 2.4G / PG 表 1.3G，-Z0 -z6）

| 路径 | 总耗时 | 峰值内存 | 瓦片 |
|---|---|---|---|
| GeoJSON | 154.3s | 685MB | 3 |
| DB（PostGIS `big_merge` 表） | **104.5s（快 32%）** | 653MB | 3 |

## 4. PG 原生传输基线（不经 tippecanoe，单线程 COPY 679 万行 → /dev/null）

| 查询 | 耗时 | 说明 |
|---|---|---|
| `SELECT ST_AsBinary(geom), to_jsonb(id)::text, ... （完整模拟 db 读行）` | 19.8s | 服务器序列化 + hex 文本传输 + 文本协议 |
| 仅 `ST_AsBinary(geom)` | 7.4s | 纯几何 hex 传输 |
| `SELECT *`（原始行，无序列化） | 9.4s | 无序列化基线 |

解读：几何 WKB hex 化+传输增量 ≈ full 19.8 − raw 9.4 ≈ 10.4s（单线程）；
tippecanoe-db 4 线程并行后有效 ~2.6s，叠加双端解析约 5-10s，
占 db 总耗时（104.5s）的 5%–10%。

## 5. 复现命令

```bash
# 小数据（PG 表 perf_points 10 万点已重建于 TippTest）
for i in 1 2 3; do
  s=$(date +%s.%N)
  ./tippecanoe-db -f -Z0 -z6 -o /tmp/perf/d$i.mbtiles \
    --postgis postgresql://postgres:postgres@127.0.0.1:5432/TippTest \
    --postgis-table perf_points --postgis-geometry-field geom 2>/tmp/perf/d$i.log
  e=$(date +%s.%N); echo "DB total=$(echo "$e-$s" | bc)"
done
# GeoJSON 路径同构，输入 /tmp/dbp2/perf.geojson；读入完成点可 awk
# '/Parallel read complete/{print systime()}' 打点。

# 大数据（TippTest.big_merge 679 万 MultiPolygon）
/usr/bin/time -f "DB total=%es peakRSS=%MKB" ./tippecanoe-db -f -Z0 -z6 \
  -o /tmp/perf/bd.mbtiles \
  --postgis postgresql://postgres:postgres@127.0.0.1:5432/TippTest \
  --postgis-table big_merge --postgis-geometry-field geom

# PG 原生基线
psql "$PG" -q -c "SET bytea_output=hex;" \
  -c "\\copy (SELECT ST_AsBinary(geom), to_jsonb(id)::text, ... FROM big_merge) TO '/dev/null'"
```

## 6. 改进空间（可选，非必须）

| 方向 | 预期收益 | 代价 |
|---|---|---|
| binary cursor（PQexecParams 二进制格式取 WKB，免 hex/文本解析） | 读入段 ~2-3% | 改读取协议与解析兜底 |
| `FORWARD` cursor 替代 `SCROLL` | 微小 | 无 |
| 属性列预序列化（替代 to_jsonb 投影） | 服务器端 CPU ~5% | 需处理键序规范化语义 |

当前不建议动：读入段占比小、瓦片管道占大头，以上改动的收益远小于回归风险。
