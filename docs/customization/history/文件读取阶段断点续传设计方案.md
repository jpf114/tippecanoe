# Tippecanoe 文件读取阶段断点续传设计方案

本文档详细设计 **阶段 A（文件读取 / radix 排序 / stringpool 合并 / shared_nodes 建立）** 的断点续传功能，与现有的阶段 B（zoom 级切片）checkpoint/resume（详见 [断点续做说明文档.md](./断点续做说明文档.md)）协同工作，实现从输入文件到最终瓦片的端到端断点续做能力。

> **状态**：设计方案（待实施）
> **作者**：基于 v3 checkpoint 架构演进
> **依赖**：v3 切片阶段 checkpoint（CRC32 / state.json / flock / SIGTERM 优雅退出）
> **当前代码版本**：v3.2（`format_version=3`，含 `name`/`description`/`attribution` 持久化）
> **目标格式版本**：v4（`format_version=4`，新增 `phase_a` 字段）

---

## 1. 背景与目标

### 1.1 问题背景

当前 tippecanoe 的 checkpoint 仅覆盖 **阶段 B（切片阶段）**：

| 阶段 | 内容 | 是否 checkpoint |
|------|------|-----------------|
| **阶段 A** | 读入 GeoJSON / CSV / FlatGeobuf → radix 排序 → 合并 stringpool → 建 shared_nodes / bloom → 计算 file_bbox | **否** |
| **阶段 B** | `traverse_zooms`：按 zoom 写 mbtiles 或目录瓦片 | **是**（每 zoom 一次） |

**痛点**：

- 大型 GeoJSON（如 100GB 的 OSM 提取数据）的 **读入 + 排序** 可能耗时数十分钟到数小时；
- 阶段 A 被 `kill -9`、OOM 或机器重启打断后，**只能从头重跑**，浪费已完成的 I/O 与计算；
- 阶段 A 的磁盘占用（各线程的 pool、vertex、geom、index 临时文件）可能高达数百 GB，重跑意味着再次产生这些临时文件；
- 在云环境（Spot 实例可能被回收、容器可能被驱逐）下，阶段 A 不可续做是显著的可靠性短板。

### 1.2 设计目标

1. **可恢复性**：阶段 A 任意时刻被中断后，能在 **最近的检查点** 续跑，不丢失已完成的工作；
2. **低开销**：checkpoint 引入的额外 I/O 与内存开销不超过阶段 A 总开销的 **10%**；
3. **兼容性**：与阶段 B checkpoint 共存，共享 `state.json`、flock、SIGTERM 优雅退出、CRC32 校验等基础设施；
4. **正确性**：恢复后的输出与从头跑 **字节级一致**（瓦片内容、metadata 完全相同）；
5. **可控粒度**：checkpoint 粒度可配置（每 N 个 feature、每 M MB、每文件），平衡开销与恢复速度。

### 1.3 非目标

- **不**支持 PMTiles 输出的阶段 A resume（与阶段 B 一致，PMTiles 不支持 resume）；
- **不**支持跨机器迁移 checkpoint（绝对路径硬编码，与阶段 B 一致）；
- **不**支持 `tippecanoe-db`（PostGIS / Mongo 输入路径），后者在后续版本考虑；
- **不**修改 radix 排序算法本身，仅在排序边界增加 checkpoint 钩子。

### 2.1 阶段 A 的子阶段划分

│   │   └── GeoJSON 序列（0x1E 分隔）/ .gz：流式分块读取 → start_parsing    │

### 2.3 资源占用分析

| 子阶段 | 内存占用 | 磁盘占用 | 主要瓶颈 |
|--------|----------|----------|----------|
| A1 并行读入 | 每线程 memfile（内存中，超过阈值后落盘） | 各线程的 `pool.XXXXXX`、`vertex.XXXXXX`、`geom.XXXXXX`、`index.XXXXXX`（共 4 × CPUS 个临时文件） | I/O 解析 + 磁盘写入 |
| A2 stringpool 合并 | mmap 各线程 pool → 拷贝到全局 pool | 全局 `pool.XXXXXX`（约等于各线程 pool 之和） | 大文件 mmap + 拷贝 |
| A3 vertex 排序 | `fqsort` 内部缓冲区（`memsize / 20`） | 临时 `vertex2.XXXXXX`、`shared_nodes.XXXXXX` | 排序 I/O + 去重扫描 |
| A4 radix 排序 | `merges` 数组 + 各段排序缓冲区 | 排序后的 `geom` 文件（约等于原始 geom 大小） | 多线程 qsort + merge I/O |
| A5 bbox 计算 | 极小 | 无 | CPU 计算 |

**关键观察**：

- A1 是 **最耗时** 的子阶段（大文件解析），也是 **最容易被中断** 的阶段；
- A2-A4 的中间产物（pool、vertex、geom、index）占用大量磁盘空间，重跑会再次产生这些文件；
- A3 的 `shared_nodes` 和 A4 的排序后 `geom` 是阶段 B 的关键输入，必须完整保存才能续跑。

### 2.4 当前异常处理

阶段 A **没有任何 checkpoint 机制**：

- 中断后所有临时文件（`/tmp/tippecanoe-pool.XXXXXX` 等）残留，由操作系统清理；
- 重跑时 `tmpdir` 下的临时文件会被 `mkstemp` 覆盖（`unlink` 后创建新的）；
- 没有进度记录，无法知道中断时完成了多少；
- `file_bbox` 等中间状态完全丢失，必须重新计算。

## 3. 设计挑战与约束

### 3.1 主要挑战

#### 挑战 1：A1 并行读入的子任务边界

A1 有两种读取模式，checkpoint 策略需分别处理：

**mmap 模式**（`do_read_parallel`）：将整个文件 mmap 后按字节偏移切分给 CPUS 个线程，切分点在 separator（换行符或 0x1E）处对齐。每个线程独立解析自己的段，**没有跨线程的进度同步**。此模式下文件内部 checkpoint 需要暂停所有线程。

**流式模式**（`start_parsing`）：主线程分块读取输入（每块 PARSE_MIN=10MB ~ PARSE_MAX=1GB），累积到阈值后启动并行解析线程处理该块。**块边界天然适合作为 checkpoint 点**，无需暂停线程，只需在两块之间的间隙写入 checkpoint。

要 checkpoint A1，需要：

- 记录每线程已处理的字节偏移（`segs[i]`）；
- 记录每线程已解析的 feature 数；
- 持久化每线程的 memfile 状态（pool、vertex、geom、index 的当前大小与内容）；
- 记录 `overall_offset`（跨文件 feature ID 唯一性）；
- 记录各线程的 `initial_x` / `initial_y` / `initialized` 状态；
- 记录各线程累积的 `file_bbox` / `file_bbox1` / `file_bbox2`。

#### 挑战 2：memfile 的内存与磁盘混合状态

`memfile` 是一个混合结构（见 [memfile.hpp](../memfile.hpp) / [memfile.cpp](../memfile.cpp)）：数据先在 `std::string map` 中累积，调用 `memfile_full()` 后切换到 `FILE *fp` 文件流模式。**此切换是单向的**：一旦 `memfile_full()` 被调用，`fp != NULL`，后续写入都走文件流，不能切回内存模式。

checkpoint 时需要：

- 若 memfile 仍在内存（`fp == NULL`）：序列化 `map` 字符串内容到 checkpoint blob；
- 若 memfile 已落盘（`fp != NULL`）：保存 fd 的当前大小（`off` 字段），并复制文件内容到 checkpoint blob；
- **恢复时的约束**：若原始 memfile 已 `memfile_full()`，恢复后必须保持文件模式（不能切回内存模式），否则后续 `memfile_full()` 调用会触发 `exit(EXIT_IMPOSSIBLE)`。

#### 挑战 3：layermaps 的累积状态

每线程维护一个 `layermap`（图层名 → `layermap_entry`），`layermap_entry` 包含 `layerseq`、`points`、`lines`、`polygons`、`retain`、`description`、`tilestats` 等。checkpoint 需要序列化完整的 `layermap` 状态。

#### 挑战 4：排序的原子性

A4 的 radix 排序包含多线程 qsort + merge，是一个 **原子操作**（要么完成，要么不开始）。checkpoint 不能在排序中间打断，只能在排序前后设置 checkpoint 点。

#### 挑战 5：磁盘空间倍增

阶段 A 的临时文件本身可能占用数百 GB。checkpoint 需要额外保存这些文件，可能导致磁盘占用翻倍。需要设计 **就地持久化** 或 **增量 checkpoint** 策略。

### 3.2 设计约束

1. **不修改核心算法**：radix 排序、fqsort、几何解析等核心逻辑不变，仅在边界增加钩子；
2. **复用 v3 基础设施**：state.json、flock、SIGTERM、CRC32、statfs 磁盘检查、异步 fsync；
3. **与阶段 B 共存**：阶段 A checkpoint 与阶段 B checkpoint 使用同一 `--checkpoint-dir`，state.json 中增加 `phase_a` 字段；
4. **向后兼容**：v3 阶段 B checkpoint 仍可独立使用（不启用阶段 A checkpoint 时行为不变）。

## 4. 断点信息定义、存储与恢复

### 4.1 阶段 A Checkpoint 状态结构

在 `CheckpointState` 中新增 `PhaseAState` 子结构：

```cpp
struct PhaseAProgress {
    // 子阶段标识（A0=0, A1=1, A2=2, A3=3, A4=4, A5=5, A_DONE=6）
    int subphase = 0;

    // A1: 并行读入进度
    struct A1ThreadProgress {
        int64_t bytes_processed = 0;      // 该线程已处理的字节数
        int64_t features_parsed = 0;       // 该线程已解析的 feature 数
        int64_t pool_size = 0;             // 该线程 pool memfile 当前大小
        int64_t vertex_size = 0;           // 该线程 vertex memfile 当前大小
        int64_t geom_size = 0;             // 该线程 geom memfile 当前大小
        int64_t index_size = 0;            // 该线程 index memfile 当前大小
        int64_t tree_size = 0;             // 该线程 tree memfile 当前大小
        int64_t node_size = 0;             // 该线程 node 文件当前大小
        // memfile 状态：true=仍在内存（fp==NULL），false=已落盘（fp!=NULL）
        bool pool_in_memory = true;
        bool vertex_in_memory = true;
        bool tree_in_memory = true;
        // 已落盘时，blob 文件路径（相对于 blobs/a1_threads/<i>/）；仍在内存时为空
        std::string pool_blob;
        std::string vertex_blob;
        std::string geom_blob;
        std::string index_blob;
        std::string tree_blob;
        std::string node_blob;
        // 该线程的 layermap 序列化（复用 v3 layermaps.bin 格式，含 description + tilestats）
        std::string layermap_blob;
        // 该线程的 initial_x / initial_y / initialized 状态
        unsigned initial_x = 0;
        unsigned initial_y = 0;
        int initialized = 0;
        // 该线程累积的 file_bbox（z=32 像素坐标）
        long long file_bbox[4] = {UINT_MAX, UINT_MAX, 0, 0};
        long long file_bbox1[4] = {0xFFFFFFFF, 0xFFFFFFFF, 0, 0};
        long long file_bbox2[4] = {0x1FFFFFFFF, 0xFFFFFFFF, 0x100000000, 0};
    };
    std::vector<A1ThreadProgress> a1_threads;  // CPUS 个

    // A1: 跨文件 feature ID 偏移（恢复 overall_offset）
    int64_t a1_overall_offset = 0;

    // A1: 输入文件处理进度（多文件场景）
    struct InputFileProgress {
        std::string path;
        int64_t size = 0;
        int64_t offset = 0;  // 已读取到的字节偏移（流式模式下为块边界）
        bool completed = false;
        int format = 0;  // 文件格式标识（用于恢复时选择正确的解析器）
    };
    std::vector<InputFileProgress> input_files_progress;
    int a1_current_source = 0;  // 当前正在处理的文件索引

    // A1: 当前累积的全局 file_bbox（所有线程合并后）
    long long a1_file_bbox[4] = {UINT_MAX, UINT_MAX, 0, 0};
    long long a1_file_bbox1[4] = {0xFFFFFFFF, 0xFFFFFFFF, 0, 0};
    long long a1_file_bbox2[4] = {0x1FFFFFFFF, 0xFFFFFFFF, 0x100000000, 0};

    // A2: stringpool 合并完成
    bool a2_pool_merged = false;
    int64_t a2_pool_total_size = 0;
    // pool_off[2*CPUS] 已持久化到 blobs/pool_off.bin（复用 v3 格式）

    // A3: shared_nodes 建立完成
    bool a3_nodes_built = false;
    int64_t a3_nodepos = 0;
    int64_t a3_bloom_size = 0;

    // A4: radix 排序完成
    bool a4_sorted = false;
    int64_t a4_geom_size = 0;  // 排序后 geom 文件大小
    // 注意：index 是中间产物，恢复时不需要，不持久化 a4_index

    // A5: iz / bbox 计算完成
    bool a5_bbox_done = false;
    int a5_iz = 0;
    int a5_basezoom = 0;
    long long a5_file_bbox[4] = {0, 0, 0, 0};
    long long a5_file_bbox1[4] = {0, 0, 0, 0};
    long long a5_file_bbox2[4] = {0, 0, 0, 0};
};

struct CheckpointState {
    // ... 既有字段 ...
    
    // v4 新增：阶段 A 状态
    PhaseAProgress phase_a;
    bool phase_a_done = false;  // 阶段 A 是否完成（snapshot_tiling_entry 已调用）
};
```

阶段 A checkpoint 在 `blobs/` 目录下新增以下文件：

| 文件 | 内容 | 何时写入 | 备注 |
|------|------|----------|------|
| `blobs/a1_threads/<i>/pool.bin` | 第 i 线程的 pool memfile 内容（含 CRC32） | A1 checkpoint 时 | memfile 内存或文件内容 |
| `blobs/a1_threads/<i>/vertex.bin` | 第 i 线程的 vertex 文件内容 | A1 checkpoint 时 | vertexfile 是 FILE*（非 memfile） |
| `blobs/a1_threads/<i>/geom.bin` | 第 i 线程的 geom 文件内容 | A1 checkpoint 时 | geomfile 是 FILE* |
| `blobs/a1_threads/<i>/index.bin` | 第 i 线程的 index 文件内容 | A1 checkpoint 时 | indexfile 是 FILE* |
| `blobs/a1_threads/<i>/tree.bin` | 第 i 线程的 tree memfile 内容 | A1 checkpoint 时 | memfile 内存或文件内容 |
| `blobs/a1_threads/<i>/node.bin` | 第 i 线程的 node 文件内容 | A1 checkpoint 时 | nodefile 是 FILE* |
| `blobs/a1_threads/<i>/layermap.bin` | 第 i 线程的 layermap 序列化 | A1 checkpoint 时 | 复用 v3 layermaps.bin 格式 |
| `blobs/a2_pool.bin` | 合并后的全局 stringpool | A2 完成时 | 就地 rename 优化（见 8.2.1） |
| `blobs/a2_pool_off.bin` | pool_off[2*CPUS] | A2 完成时 | 复用 v3 pool_off.bin 格式 |
| `blobs/a3_shared_nodes.bin` | shared_nodes 文件 | A3 完成时 | 含 shared_nodes_map |
| `blobs/a3_bloom.bin` | shared_nodes_bloom | A3 完成时 | 自适应大小 |
| `blobs/a4_geom.bin` | 排序后的 geom 文件 | A4 完成时 | 就地 rename 优化；**不保存 index**（中间产物，恢复时不需要） |

**注意**：`vertex` / `geom` / `index` / `node` 在 `readers[i]` 中是 `FILE *`（非 memfile），使用 `fopen_oflag` 打开，有独立的 fd。checkpoint 时需要 `fflush` + `fsync` 后复制内容。`pool` 和 `tree` 是 `memfile` 结构，需根据 `fp == NULL` 判断状态。

### 4.4 指纹扩展

`compute_fingerprint` 需要纳入阶段 A 相关参数：

- `--read-parallel` / `-P` 参数；
- 输入文件的 `content_hash`（v3 已有）；
- `CPUS`、`TEMP_FILES`（已有）；
- **不**纳入 `subphase` 等进度字段（这些是可变的）。

指纹仍用于 **内部一致性校验**（state.json 未被篡改），不校验当前命令行。

### 4.5 恢复时的校验

恢复阶段 A checkpoint 时，进行以下校验：

1. **指纹校验**：`verify_fingerprint_internal()`（复用现有逻辑）；
2. **CRC32 校验**：所有 blob 文件校验 CRC32（复用 v3 的 `read_blob_with_crc` / `verify_mmap_crc`）；
3. **输入文件校验**：`stat_input_paths()` 重新 stat 输入文件，比较 `size`、`mtime_sec`、`mtime_nsec`、`content_hash`（v3）；
4. **磁盘空间校验**：`check_disk_space()` 预检恢复所需空间；
5. **flock 锁**：`acquire_lock()` 防止并发 resume。

## 5. 读取进度的精确记录与校验方案

### 5.1 A1 并行读入的进度记录

#### 5.1.1 Checkpoint 触发时机

A1 的 checkpoint 触发策略按读取模式区分：

**流式模式（推荐，天然支持块边界 checkpoint）**：

| 策略 | 触发条件 | 适用场景 |
|------|----------|----------|
| **按块边界** | 每个流式块（PARSE_MIN~PARSE_MAX）解析完成后触发 | GeoJSON 序列 / .gz 文件 |
| **按文件** | 每个输入文件完成时触发一次 | 多文件场景 |

流式模式下，主线程在 `start_parsing` 返回后（即上一块解析完成、下一块开始前）插入 checkpoint 调用，**无需暂停线程**，因为此时所有解析线程已 `pthread_join` 完成。

**mmap 模式（需暂停线程或等待完成）**：

| 策略 | 触发条件 | 适用场景 |
|------|----------|----------|
| **按文件** | 每个输入文件完成时触发一次（推荐） | 小文件 / FlatGeobuf / CSV |
| **按 feature 数** | 每 N 个 feature 触发一次（需暂停线程） | 大文件内部 checkpoint |
| **禁用** | 不触发 A1 checkpoint（仅 A2/A3/A4/A5 边界 checkpoint） | 小数据集 |

通过 `--checkpoint-a1-interval=N` 参数配置，`N=0` 表示禁用 A1 文件内 checkpoint（仅保留文件边界 checkpoint）。

#### 5.1.2 进度记录内容

每次 A1 checkpoint 触发时，记录：

```cpp
struct A1Checkpoint {
    int64_t timestamp;                    // Unix 时间戳
    std::vector<A1ThreadProgress> threads; // CPUS 个线程的进度
    std::vector<InputFileProgress> files;  // 输入文件进度
    int64_t overall_offset;               // 跨文件 feature ID 偏移
    int current_source;                   // 当前处理的文件索引
    long long file_bbox[4];               // 当前的累积 bbox（全局合并）
    long long file_bbox1[4];
    long long file_bbox2[4];
};
```

#### 5.1.3 memfile 状态持久化

对每个线程的 memfile（pool、tree），根据其当前状态采取不同策略：

| memfile 状态 | 持久化方式 | 恢复方式 |
|-------------|-----------|----------|
| 仍在内存（`fp == NULL`） | 序列化 `map` 字符串到 `blobs/a1_threads/<i>/<name>.bin`（含 CRC32） | 读入内存 `map`，保持 `fp == NULL` |
| 已落盘（`fp != NULL`） | `fflush` + `fsync` + 复制 fd 内容到 blob（含 CRC32），使用 `sendfile` 零拷贝 | 写入新 fd，调用 `memfile_full()` 切换到文件模式 |

对非 memfile 的 `FILE *`（vertex、geom、index、node），直接 `fflush` + `fsync` + 复制文件内容到 blob。

**恢复时的关键约束**：若原始 memfile 已 `memfile_full()`（`fp != NULL`），恢复后必须立即调用 `memfile_full()` 切换到文件模式，否则后续 `memfile_full()` 会触发 `exit(EXIT_IMPOSSIBLE)`。

#### 5.1.4 并发安全

**流式模式**（推荐）：无需暂停线程。`start_parsing` 内部通过 `pthread_join` 等待所有解析线程完成后返回，主线程在返回后插入 checkpoint 调用。

**mmap 模式**（文件内 checkpoint）：需要暂停正在解析的线程：

1. 主线程发送 `SIGUSR2` 给所有读入线程，线程在下一个 feature 边界暂停；
2. 主线程等待所有线程确认暂停（使用 `pthread_barrier_t` 或原子计数器）；
3. 主线程收集各线程状态，写入 checkpoint；
4. 主线程发送信号唤醒所有线程继续。

**简化方案**（首版实现）：A1 checkpoint 仅在 **输入文件边界** 触发，即一个文件读完后、下一个文件开始前（main.cpp L1522 的 `for (source = 0; source < nsources; source++)` 循环中）。这样无需暂停线程，只需在主线程的文件循环中插入 checkpoint 调用。

**流式模式的额外优势**：流式模式天然在块边界（PARSE_MIN~PARSE_MAX）同步，可在块边界插入 checkpoint，实现文件内增量 checkpoint 而无需暂停线程。这是 Phase 3 的推荐实现路径。

### 5.2 A2-A5 的进度记录

A2-A5 是 **串行** 子阶段，checkpoint 在每个子阶段完成时触发：

| 子阶段 | Checkpoint 触发点 | 持久化内容 |
|--------|------------------|-----------|
| A2 完成 | stringpool 合并后 | `a2_pool.bin`、`a2_pool_off.bin`、`subphase=2` |
| A3 完成 | shared_nodes 建立后 | `a3_shared_nodes.bin`、`a3_bloom.bin`、`subphase=3` |
| A4 完成 | radix 排序后 | `a4_geom.bin`、`a4_index.bin`（可选）、`subphase=4` |
| A5 完成 | iz/bbox 计算后 | 在 state.json 中记录 `a5_*` 字段、`subphase=5` |
| A 完成 | `snapshot_tiling_entry` 调用后 | `phase_a_done=true`（此时阶段 B checkpoint 接管） |

### 5.3 校验方案

#### 5.3.1 恢复时的完整校验流程

```
resume A 阶段 checkpoint:
  ├── 1. 指纹校验（verify_fingerprint_internal）
  ├── 2. 输入文件 stat 校验（size + mtime + content_hash）
  ├── 3. 磁盘空间预检（check_disk_space）
  ├── 4. flock 锁获取
  ├── 5. 根据 subphase 恢复：
  │   ├── subphase == 1: 加载 a1_threads/*.bin，恢复各 memfile
  │   │   ├── 校验每个 blob 的 CRC32
  │   │   ├── 从 memfile 重建内存或映射 fd
  │   │   ├── 恢复各线程的 layermap
  │   │   └── 从 input_files_progress 跳过已处理部分
  │   ├── subphase == 2: 加载 a2_pool.bin，mmap 为 stringpool
  │   │   └── 跳过 A1、A2，从 A3 开始
  │   ├── subphase == 3: 加载 a3_*.bin，恢复 shared_nodes
  │   │   └── 跳过 A1-A3，从 A4 开始
  │   ├── subphase == 4: 加载 a4_geom.bin，恢复排序后 geom
  │   │   └── 跳过 A1-A4，从 A5 开始
  │   └── subphase == 5: 直接进入 snapshot_tiling_entry → 阶段 B
  └── 6. 恢复 file_bbox 等中间状态
```

#### 5.3.2 memfile 恢复的完整性校验

每个 memfile 恢复后，校验：

- **CRC32**：blob 文件的 CRC32（v3 已有）；
- **大小**：`pool_size` 字段与实际文件大小一致；
- **feature 数**：解析前几个 feature 验证格式正确性（可选，开销较大）。

#### 5.3.3 layermap 恢复的完整性

layermap 使用 v3 序列化格式（含 `description` + `tilestats`），恢复后：

- 校验 `layermap_entry.layerseq` 与 `a1_threads[i].features_parsed` 一致；
- 校验图层名集合与指纹中的输入文件列表一致。

## 6. 异常中断后的恢复流程设计

### 6.1 恢复流程总览

```
用户执行: tippecanoe --resume=/checkpoint/dir

  ├── read_resume_info() 读取 state.json
  │   ├── phase_a_done == true?
  │   │   └── 是: 走阶段 B resume 流程（现有逻辑）
  │   └── 否: 走阶段 A resume 流程（新逻辑）
  │
  ├── 阶段 A resume 流程:
  │   ├── 1. 校验 fingerprint + 输入文件 + 磁盘空间 + flock
  │   ├── 2. 根据 subphase 恢复中间状态
  │   ├── 3. 从断点子阶段继续执行:
  │   │   ├── subphase == 1: 继续读入剩余输入文件 → A2 → A3 → A4 → A5 → snapshot_tiling_entry
  │   │   ├── subphase == 2: A3 → A4 → A5 → snapshot_tiling_entry
  │   │   ├── subphase == 3: A4 → A5 → snapshot_tiling_entry
  │   │   ├── subphase == 4: A5 → snapshot_tiling_entry
  │   │   └── subphase == 5: snapshot_tiling_entry → 阶段 B resume
  │   └── 4. 阶段 A 完成后，phase_a_done = true，转入阶段 B resume
  │
  └── 阶段 B resume 流程（现有逻辑）:
      └── restore_tiling() → traverse_zooms() 从 last_completed_zoom+1 继续
```

### 6.2 子阶段恢复的详细逻辑

#### 6.2.1 subphase == 1（A1 中断恢复）

```
1. 恢复 overall_offset 和 current_source:
   a. 从 state.json 读取 a1_overall_offset 和 a1_current_source
   b. 设置 overall_offset = a1_overall_offset
   c. 从 input_files_progress 跳过已完成的文件（completed == true）

2. 为每个线程 i (0..CPUS-1):
   a. 读取 blobs/a1_threads/<i>/pool.bin
      - 校验 CRC32
      - 重建 memfile:
        - 若 pool_in_memory == true: 读入内存 map，保持 fp == NULL
        - 若 pool_in_memory == false: 写入新 fd，调用 memfile_full() 切换到文件模式
      - 设置 readers[i].poolfile->off = pool_size
   b. 同样恢复 tree memfile（同 pool 逻辑）
   c. 恢复 vertex / geom / index / node（FILE*，写入新 fd 并 fopen）
      - 设置 readers[i].vertexpos / geompos / indexpos / nodepos
   d. 读取 layermap_blob，反序列化为 layermap（复用 v3 layermaps.bin 反序列化逻辑）
   e. 恢复 initial_x[i] / initial_y[i] / initialized[i]
   f. 恢复 readers[i].file_bbox / file_bbox1 / file_bbox2

3. 恢复全局 file_bbox:
   - 从 state.json 读取 a1_file_bbox / a1_file_bbox1 / a1_file_bbox2
   - 设置为全局 file_bbox 的初始值（后续文件继续累积）

4. 从 a1_current_source 开始继续处理剩余输入文件:
   - 跳过 completed == true 的文件
   - 对于当前文件（completed == false）:
     - 流式模式: fseek 到 offset 位置，继续分块读取
     - mmap 模式: mmap 后从 offset 位置开始（需处理 separator 对齐）
   - 继续解析剩余部分到对应的线程 memfile / FILE*

5. 所有输入文件处理完成后，转入 A2
```

**关键技术问题与解决方案**：

1. **separator 对齐**：
   - A1 checkpoint 时，`offset` 记录的是已处理的字节位置，保证在 separator（`\n` 或 `0x1E`）边界上；
   - 流式模式下，`offset` 是块边界（`PARSE_MIN` 的整数倍），天然对齐；
   - mmap 模式下，`offset` 是 `do_read_parallel` 的 `segs[CPUS]`（文件末尾）或文件边界；
   - 恢复时从 `offset` 位置开始读取，不需要跳过不完整 feature。

2. **overall_offset 的恢复**：
   - `overall_offset` 用于跨文件 feature ID 唯一性（`layer_seq[i] = segs[i] + initial_offset`）；
   - 恢复时从 `a1_overall_offset` 继续，确保 feature ID 连续不重复。

3. **initial_x / initial_y / initialized 的恢复**：
   - 这些值在每个线程首次解析 feature 时设置（`initialized[i] == 0` 时）；
   - 恢复时若 `initialized[i] == 1`，后续解析不会覆盖这些值；
   - 必须正确恢复，否则 `pool_off` 计算会出错。

4. **file_bbox 的累积恢复**：
   - `file_bbox` 是各线程在解析过程中累积的（`readers[i].file_bbox`）；
   - 全局 `file_bbox` 是所有线程的合并（`choose_first_zoom` 中计算）；
   - 恢复时需要同时恢复各线程的 `file_bbox` 和全局 `file_bbox`。

5. **layermap 的合并恢复**：
   - 每线程的 layermap 独立序列化；
   - 恢复后不需要合并（合并在 A2/A3 后由 `merge_layermaps` 完成）；
   - 但需确保 `layermap_entry.layerseq` 与 `features_parsed` 一致。

#### 6.2.2 subphase == 2-5 的恢复

这些子阶段的恢复相对简单，因为它们是串行的，且输出是完整的文件：

```
subphase == 2:
  - mmap blobs/a2_pool.bin 为 stringpool
  - 读取 pool_off[2*CPUS]
  - 从 A3 开始执行

subphase == 3:
  - mmap blobs/a3_shared_nodes.bin 为 shared_nodes_map
  - 读取 blobs/a3_bloom.bin 为 shared_nodes_bloom
  - 从 A4 开始执行

subphase == 4:
  - 读取 blobs/a4_geom.bin 为 geomfd[0]
  - 从 A5 开始执行

subphase == 5:
  - 读取 state.json 中的 a5_* 字段
  - 直接调用 snapshot_tiling_entry → 阶段 B
```

### 6.3 异常清理

阶段 A resume 时，需要清理上次中断可能留下的残留：

1. **临时文件清理**：`tmpdir` 下的 `tippecanoe-pool.XXXXXX` 等文件（由 `mkstemp` + `unlink` 创建，中断后可能残留）；
2. **staging 目录清理**：`checkpoint_dir/staging/` 下未完成的 blob 文件；
3. **state.json.tmp 清理**：上次写入未完成的临时文件。

清理逻辑复用现有的 `clear_workspace()` 与 `rmrf_path()`。

### 6.4 异常场景与处理机制

#### 6.4.1 Checkpoint 写入过程中的异常

| 异常场景 | 处理机制 | 退出码 |
|----------|----------|--------|
| Checkpoint 写入时磁盘满 | `check_disk_space()` 预检 + 写入失败时回滚 staging | `EXIT_CHECKPOINT=121` |
| Checkpoint 写入时进程被 kill -9 | staging 目录残留，state.json 未更新；resume 时清理 staging | 下次 resume 自动恢复 |
| fsync 过程中进程被 kill -9 | blob 文件可能未完全落盘；resume 时 CRC32 校验失败 | `EXIT_CHECKPOINT=121` |
| state.json 原子 rename 失败 | state.json.tmp 残留，state.json 保持旧版本 | 下次 resume 使用旧版本 |
| 多线程解析中某线程失败 | 主线程 `pthread_join` 检测到错误，触发整体退出 | 对应错误码 |

#### 6.4.2 恢复过程中的异常

| 异常场景 | 处理机制 | 退出码 |
|----------|----------|--------|
| Blob 文件 CRC32 校验失败 | 拒绝恢复，提示用户从 scratch 重跑 | `EXIT_CHECKPOINT=121` |
| memfile 大小与 state.json 记录不一致 | 拒绝恢复，提示 checkpoint 损坏 | `EXIT_CHECKPOINT=121` |
| 输入文件被修改或删除 | `stat_input_paths()` 校验 size/mtime/content_hash 失败 | `EXIT_ARGS=101` |
| 输入文件不可 seek（如管道） | 检测到非普通文件时拒绝 A1 checkpoint | `EXIT_ARGS=101` |
| layermap 反序列化失败 | 拒绝恢复，提示 checkpoint 损坏 | `EXIT_CHECKPOINT=121` |
| flock 获取失败（并发 resume） | 拒绝启动，提示已有进程在 resume | `EXIT_EXISTS=104` |
| `phase_a_done` 与 blob 状态矛盾 | `verify_blobs_consistency()` 检测到不一致 | `EXIT_CHECKPOINT=121` |

#### 6.4.3 SIGTERM/SIGINT 在阶段 A 的处理

阶段 A 执行期间收到 SIGTERM/SIGINT 时，按当前子阶段采取不同策略：

| 当前子阶段 | SIGTERM 处理策略 | 退出码 |
|------------|-----------------|--------|
| A1（文件边界） | 等待当前文件解析完成，触发 A1 checkpoint，退出 | `EXIT_INCOMPLETE=100` |
| A1（文件内部，流式模式） | 等待当前块解析完成（`pthread_join` 返回），触发 checkpoint，退出 | `EXIT_INCOMPLETE=100` |
| A1（文件内部，mmap 模式） | 等待所有线程 `pthread_join` 完成，触发 checkpoint，退出 | `EXIT_INCOMPLETE=100` |
| A2（stringpool 合并） | 完成合并后触发 checkpoint，退出 | `EXIT_INCOMPLETE=100` |
| A3（vertex 排序） | 完成排序后触发 checkpoint，退出 | `EXIT_INCOMPLETE=100` |
| A4（radix 排序） | 完成排序后触发 checkpoint，退出 | `EXIT_INCOMPLETE=100` |
| A5（bbox 计算） | 完成计算后触发 checkpoint，退出 | `EXIT_INCOMPLETE=100` |

**关键约束**：

- A2-A4 的排序操作是 **原子操作**，不能在排序中间打断（数据可能不一致）；
- SIGTERM 处理器只设置 `g_shutdown_requested = 1` 标志，由主循环在安全点检查；
- 排序过程中不检查 `g_shutdown_requested`，排序完成后才检查；
- 退出前确保 checkpoint 已落盘（`wait_pending_fsync()` + `save_state_atomic()`）。

## 7. 与现有切片阶段断点续传的兼容性

### 7.1 state.json 共存

阶段 A 和阶段 B 的 checkpoint 共用同一个 `state.json`：

```json
{
  "format_version": 4,
  "fingerprint": "...",
  "phase_a": { ... },          // v4 新增
  "phase_a_done": false,       // v4 新增
  "tiling": { ... },           // 阶段 B 状态（phase_a_done=true 后才有意义）
  "zoom_commits": { ... },     // 阶段 B 的 zoom 提交记录
  "current_gen_files": [ ... ] // 阶段 B 的世代索引
}
```

**关键不变量**：

- `phase_a_done == false` 时，`tiling` / `zoom_commits` / `current_gen_files` 字段应为空或默认值；
- `phase_a_done == true` 时，`phase_a` 字段保留作为历史记录，不再更新；
- `snapshot_tiling_entry` 调用前，必须先设置 `phase_a_done = true`。

### 7.2 命令行参数兼容

| 参数 | 阶段 A 行为 | 阶段 B 行为 |
|------|------------|------------|
| `--checkpoint-dir=DIR` | 启用阶段 A checkpoint | 启用阶段 B checkpoint（现有） |
| `--resume=DIR` | 若 `phase_a_done == false`，恢复阶段 A | 若 `phase_a_done == true`，恢复阶段 B（现有） |
| `--checkpoint-status=DIR` | 显示阶段 A 进度 + 阶段 B 进度 | 同左 |
| `--checkpoint-prune=DIR` | 清理所有 blobs（含 `a1_threads/`、`a2_*` 等） | 清理所有 blobs（现有） |
| `--checkpoint-force` | 强制覆盖现有 checkpoint（含阶段 A） | 同左 |
| `--checkpoint-a1-interval=N` | **v4 新增**：A1 checkpoint 间隔 | 无影响 |

### 7.3 flock 与 SIGTERM 的复用

- **flock**：阶段 A resume 同样获取 `checkpoint_dir/.lock` 的 `LOCK_EX | LOCK_NB`，与阶段 B 共享；
- **SIGTERM/SIGINT**：阶段 A 执行期间也注册信号处理器，收到信号后：
  - 若在 A1 读入中：等待当前 feature 处理完，触发一次 A1 checkpoint，然后退出；
  - 若在 A2-A5 中：完成当前子阶段，触发 checkpoint，然后退出；
  - 退出码仍为 `EXIT_INCOMPLETE=100`。

### 7.4 向后兼容

#### 版本演进路径

当前代码版本为 v3.2（`format_version=3`，含 `name`/`description`/`attribution` 持久化）。本方案引入 v4（`format_version=4`），新增 `phase_a` 和 `phase_a_done` 字段。

#### 兼容性矩阵

| 场景 | 行为 |
|------|------|
| **v4 代码读取 v3/v3.2 state.json** | `phase_a` 字段缺省为空，`phase_a_done` 缺省为 `false`；但 v3 的 `entry_snapshot_done == true` 意味着阶段 A 已完成，v4 代码推断 `phase_a_done = true`，走阶段 B resume 路径 |
| **v3/v3.2 代码读取 v4 state.json** | v3 代码忽略 `phase_a` 和 `phase_a_done` 字段，按现有逻辑恢复阶段 B（`entry_snapshot_done` 仍存在） |
| **v4 代码读取 v4 state.json（phase_a_done=false）** | 走阶段 A resume 路径（新逻辑） |
| **v4 代码读取 v4 state.json（phase_a_done=true）** | 走阶段 B resume 路径（现有逻辑） |
| **v4 代码读取 v3 blob** | 阶段 B 的 blob（如 `geom.initial`）可能没有 CRC32，v4 代码通过 `blob_has_crc()` 判断（基于 `format_version >= 3`） |
| **v4 阶段 A blob 与 v3 阶段 B blob 共存** | 阶段 A blob 在 `blobs/a1_threads/`、`blobs/a2_*` 等子目录/前缀下，不与阶段 B blob 冲突 |

#### 关键不变量

- `format_version` 从 3 升级到 4 是 **单向** 的：v4 代码写入的 state.json 的 `format_version=4`，v3 代码读取时不会报错（忽略未知字段），但 v3 代码 **不会写入** `phase_a` 字段；
- `entry_snapshot_done` 字段在 v4 中保留，与 `phase_a_done` 的关系：`phase_a_done == true` 蕴含 `entry_snapshot_done == true`（但反之不成立，因为 `entry_snapshot_done` 可能在 `snapshot_tiling_entry` 调用前为 false）；
- `snapshot_tiling_entry` 调用前，必须先设置 `phase_a_done = true` 和 `entry_snapshot_done = true`。

#### 迁移策略

- **无需主动迁移**：v3 checkpoint 目录可直接被 v4 代码 resume（走阶段 B 路径）；
- **v4 checkpoint 目录无法被 v3 代码 resume 阶段 A**：v3 代码不识别 `phase_a_done == false`，会尝试走阶段 B 路径，但 `entry_snapshot_done == false` 会导致退出码 101；
- **降级场景**：若需从 v4 降级到 v3，只需删除 `phase_a` 和 `phase_a_done` 字段，保留 `entry_snapshot_done` 即可。

## 8. 性能影响评估及优化策略

### 8.1 性能开销模型

阶段 A checkpoint 的额外开销：

```
 overhead = Σ (checkpoint 次数 × 每次 checkpoint 开销)
 
 每次 checkpoint 开销 = 
     blob 写入 I/O + CRC32 计算 + state.json 序列化 + fsync
```

#### 8.1.1 A1 checkpoint 开销

每次 A1 checkpoint 需要持久化 CPUS 个线程的 memfile + FILE*（pool、tree、vertex、geom、index、node，共 6 × CPUS 个文件）。**注意：memfile 是累积的**，后期 checkpoint 的 memfile 大小远大于前期。

假设每次 checkpoint 时各线程的累积数据总大小为 `S`：

- **blob 写入 I/O**：`S` 字节（顺序写）
- **CRC32 计算**：`S` 字节（CPU 计算，约 2GB/s，可忽略）
- **state.json 序列化**：< 10KB（可忽略）
- **fsync**：每个 blob 文件 1 次 + state.json 1 次；SSD 约 1-10ms/次，HDD 约 10-30ms/次

**示例（SSD）**：100GB 输入，CPUS=16，每 100MB 输入数据 checkpoint 一次：
- **关键修正**：memfile 是累积的，第 N 次 checkpoint 时 `S ≈ N × 100MB × 扩展系数`（扩展系数取决于 feature 的属性大小和几何复杂度，通常 1.5-3x）
- 假设扩展系数 2x，第 N 次 checkpoint 的 `S ≈ N × 200MB`
- checkpoint 次数 = 1000
- 总开销 = Σ(N=1..1000) (N × 200MB / 200MB/s + 6×16×5ms) ≈ 积分计算
- **首版（文件边界 checkpoint）**：假设 10 个文件，每文件完成后 checkpoint 一次：
  - 最后一次 checkpoint 的 `S ≈ 20GB`（累积全部）
  - 总开销 ≈ 10 × (10GB 平均 / 200MB/s + 5s fsync) ≈ 500s + 50s = 550s
  - 阶段 A 总耗时（假设）= 3600s
  - **开销比例 ≈ 15%**（可通过增量 checkpoint 优化）

**示例（HDD）**：同样场景，fsync 开销显著增加：
- HDD 顺序写约 100-150MB/s，fsync 约 10-30ms/次
- 总开销 ≈ 10 × (10GB / 120MB/s + 10s fsync) ≈ 830s + 100s = 930s
- **开销比例 ≈ 26%**（HDD 上建议禁用 A1 文件内 checkpoint）

**结论**：A1 文件内 checkpoint 在 SSD 上开销可控（< 15%），在 HDD 上建议禁用（`--checkpoint-a1-interval=0`），仅保留文件边界 checkpoint。

#### 8.1.2 A2-A5 checkpoint 开销

A2-A5 的 checkpoint 次数少（每个子阶段 1 次），但单次开销大：

- A2: 持久化全局 pool（可能数十 GB）
- A3: 持久化 shared_nodes + bloom（通常 < 1GB）
- A4: 持久化排序后 geom（可能数十 GB）
- A5: 仅 state.json 更新（可忽略）

**A2 和 A4 的开销**主要是磁盘 I/O（拷贝大文件），但这是 **一次性** 的，且可以通过 **就地持久化** 优化。

### 8.2 优化策略

#### 8.2.1 就地持久化（A2、A4）

A2 的全局 pool 和 A4 的排序后 geom 本身就是临时文件，可以 **直接 rename** 到 `blobs/` 目录，避免拷贝：

```cpp
// A2 完成后
rename(tmp_pool_path, checkpoint_dir + "/blobs/a2_pool.bin");
// 追加 CRC32（流式计算）
append_crc32(checkpoint_dir + "/blobs/a2_pool.bin", pool_crc);
```

**注意**：rename 跨文件系统时需要 fallback 到拷贝。检查 `tmpdir` 与 `checkpoint_dir` 是否在同一文件系统。

#### 8.2.2 增量 checkpoint（A1）

A1 的 memfile 是 **追加写入** 的，可以采用增量 checkpoint：

- 首次 checkpoint：持久化完整 memfile；
- 后续 checkpoint：仅持久化增量部分（`prev_size → current_size`）；
- 恢复时：依次重放增量，重建完整 memfile。

**实现复杂度**：中等。需要维护增量文件列表，恢复时按顺序合并。

**适用场景**：大文件（> 10GB）的 A1 读入，checkpoint 间隔较小（< 100MB）。

#### 8.2.3 异步 CRC32（A1）

CRC32 计算可以 **异步** 进行，不阻塞读入线程：

```cpp
// 读入线程写入 memfile 后
async_compute_crc(memfile_chunk, [chunk_id](uint32_t crc) {
    // CRC 计算完成后，更新 state.json 中的 crc 记录
});
```

**注意**：CRC32 计算速度（~2GB/s）远快于磁盘 I/O（~200MB/s），异步的收益有限，首版可不做。

#### 8.2.4 自适应 checkpoint 间隔

根据阶段 A 的实际进度自动调整 checkpoint 间隔：

- 初始间隔：`--checkpoint-a1-interval` 指定的值；
- 若单次 checkpoint 开销 > 阶段 A 剩余耗时的 20%，自动延长间隔；
- 若单次 checkpoint 开销 < 阶段 A 剩余耗时的 5%，自动缩短间隔。

#### 8.2.5 禁用 A1 checkpoint 的快速路径

对于小文件（< 1GB）或快速解析场景，允许通过 `--checkpoint-a1-interval=0` 禁用 A1 checkpoint，仅保留 A2-A5 边界 checkpoint。这样开销几乎为零，但 A1 中断后仍需重跑整个 A1。

### 8.3 磁盘空间评估

阶段 A checkpoint 的额外磁盘占用：

| 场景 | 额外磁盘占用 |
|------|-------------|
| A1 增量 checkpoint | 每次 checkpoint 增量约 `4 × CPUS × interval`（如 100MB 间隔 × 16 CPU = 1.6GB/次） |
| A2 就地持久化 | 0（rename，无额外占用） |
| A3 持久化 | `shared_nodes + bloom`（通常 < 1GB） |
| A4 就地持久化 | 0（rename） |
| A5 | 0（仅 state.json） |

**最坏情况**：100GB 输入，A1 checkpoint 10 次，每次增量 1.6GB，总额外占用 = 16GB。需在 `check_disk_space()` 中预留。

## 9. 分阶段实施计划

### 9.1 Phase 1：基础设施与 A2-A5 checkpoint（MVP）

**目标**：实现 A2-A5 子阶段边界 checkpoint，A1 中断后仍需重跑，但 A2-A5 中断后可续跑。

**实施内容**：

1. 在 `CheckpointState` 中增加 `PhaseAProgress` 结构（仅 `subphase`、`a2_*`、`a3_*`、`a4_*`、`a5_*` 字段）；
2. 将 `TIPPECANOE_CHECKPOINT_FORMAT` 从 3 升级到 4；
3. 在 `main.cpp::read_input` 的 A2（L2006+）、A3（L2097+）、A4（L2324 radix 调用后）、A5（L2307 choose_first_zoom 后）完成点插入 checkpoint 调用；
4. 实现 `blobs/a2_pool.bin`、`a3_shared_nodes.bin`、`a4_geom.bin` 的写入与读取（含 CRC32，复用 v3 的 `write_blob_with_crc` / `read_blob_with_crc`）；
5. 实现 `restore_phase_a()` 函数，根据 `subphase` 恢复 A2-A5 状态；
6. 修改 `can_resume_tiling()` 逻辑：当 `phase_a_done == false` 时走阶段 A resume 路径；
7. 在 `read_resume_info` 与 `Session::open_resume` 中处理 `phase_a_done == false` 的情况；
8. 复用 v3 的 `check_disk_space`、`async_fsync_blob_dir`、`flock`、SIGTERM 处理。

**关键修改点**：

- [checkpoint.hpp](../checkpoint.hpp) L76：`CheckpointState` 增加 `PhaseAProgress phase_a` 和 `bool phase_a_done` 字段；
- [checkpoint.cpp](../checkpoint.cpp) L1654：`can_resume_tiling()` 增加阶段 A 判断；
- [main.cpp](../main.cpp) L1223：`read_input` 开头的 resume 分支增加阶段 A 判断。

**测试**：见 9.5 测试矩阵的 Phase 1 部分。

**预期收益**：阶段 A 的后 4 个子阶段（约占总耗时的 30-50%）可续跑。

### 9.2 Phase 2：A1 单文件边界 checkpoint

**目标**：在 A1 的输入文件边界实现 checkpoint，多文件场景下单个文件完成后可续跑。

**实施内容**：

1. 在 `PhaseAProgress` 中增加 `input_files_progress`、`a1_threads`、`a1_overall_offset`、`a1_file_bbox*` 字段；
2. 在 [main.cpp](../main.cpp) L1522 的 `for (source = 0; source < nsources; source++)` 循环中，每个文件完成后（`checkdisk` 调用前）触发 checkpoint；
3. 持久化当前所有线程的 memfile + FILE* 状态（pool、tree、vertex、geom、index、node）到 `blobs/a1_threads/<i>/`；
4. 持久化各线程的 layermap（复用 v3 layermaps.bin 序列化逻辑）；
5. 持久化 `overall_offset`、`initial_x/y`、`initialized`、各线程 `file_bbox`；
6. 实现 `restore_a1()` 函数，恢复 memfile、FILE*、layermap 与各状态；
7. 在恢复后的 A1 中，跳过 `completed == true` 的文件，从 `a1_current_source` 继续。

**限制**：
- 单个大文件（如 100GB GeoJSON）中断后仍需重跑整个文件；
- 不支持文件内部的进度 checkpoint；
- FlatGeobuf / Geobuf / CSV 格式目前使用专用解析器（非 `do_read_parallel`），需确认其 memfile 状态是否可 checkpoint（这些格式 mmap 整个文件，解析过程类似）。

**测试**：见 9.5 测试矩阵的 Phase 2 部分。

**预期收益**：多文件场景（如分省 GeoJSON）的阶段 A 可续跑。

### 9.3 Phase 3：A1 文件内增量 checkpoint

**目标**：在 A1 的文件内部实现增量 checkpoint，大文件中断后可从断点续跑。

**实施路径（按读取模式区分）**：

**路径 A：流式模式（推荐优先实现）**

流式模式天然在块边界（PARSE_MIN~PARSE_MAX）同步，实现简单：

1. 在 `PhaseAProgress` 中增加 `a1_threads` 的 `bytes_processed`、`features_parsed` 字段；
2. 实现 `--checkpoint-a1-interval=N` 参数解析（N 为块数间隔，默认 1）；
3. 在 [main.cpp](../main.cpp) L1861 的 `start_parsing` 调用后（`pthread_join` 完成后）插入 checkpoint 钩子；
4. 持久化各线程的累积 memfile 状态（同 Phase 2）；
5. 恢复时 `fseek` 到 `offset` 位置，继续流式读取。

**优势**：无需暂停线程（`start_parsing` 内部已 `pthread_join`），实现简单。

**路径 B：mmap 模式（复杂，可选实现）**

mmap 模式下 `do_read_parallel` 一次性处理整个文件，需暂停线程：

1. 实现线程暂停 / 恢复机制（`SIGUSR2` + `pthread_barrier_t`）；
2. 在 `do_read_parallel` 的 `pthread_join` 循环中插入 checkpoint 检查点；
3. 持久化各线程的 `segs[i]` 偏移与 memfile 状态；
4. 恢复时重新 mmap 文件，从已处理偏移继续。

**复杂度评估**：路径 B 需要 **重大重构**（修改 `do_read_parallel` 的线程管理逻辑），建议推迟到 Phase 4 或仅在流式模式不可用时实现。

**增量 checkpoint 优化**（两个路径通用）：

1. 首次 checkpoint：持久化完整 memfile；
2. 后续 checkpoint：仅持久化增量部分（`prev_size → current_size`）；
3. 恢复时：依次重放增量，重建完整 memfile；
4. 需维护增量文件列表，恢复时按顺序合并。

**测试**：见 9.5 测试矩阵的 Phase 3 部分。

**预期收益**：任意时刻的阶段 A 中断都可续跑，最大丢失工作量 = `checkpoint_a1_interval`。

### 9.4 Phase 4：优化与打磨

**目标**：性能优化与用户体验提升。

**实施内容**：

1. 实现就地持久化（A2、A4 的 rename 优化，需检查 `tmpdir` 与 `checkpoint_dir` 是否同一文件系统）；
2. 实现自适应 checkpoint 间隔（根据单次 checkpoint 开销动态调整）；
3. 在 `--checkpoint-status` 中显示阶段 A 进度（`subphase`、已处理字节数、预估剩余时间）；
4. 实现增量 checkpoint 的空间回收（旧增量文件清理）；
5. 文档更新与测试用例补充；
6. 性能基准测试（对比 v3 与 v4 的阶段 A 开销，SSD / HDD 分别测试）。

## 10. 修订摘要

本方案经基于代码实际实现的系统性审阅后，进行了以下关键完善：

### 10.1 修正的不准确描述

| 问题 | 原描述 | 修正后 |
|------|--------|--------|
| A1 读取模式 | "将大文件按 separator 切分给 CPUS 个线程" | 区分 mmap 模式（`do_read_parallel`）和流式模式（`start_parsing`），两者 checkpoint 策略不同 |
| memfile 行为 | 未说明 `memfile_full()` 的单向性 | 明确 `memfile_full()` 是单向切换，恢复时必须保持文件模式 |
| 性能开销估算 | 假设每次 checkpoint 的 `S ≈ 100MB` | 修正为累积大小（`S ≈ N × interval × 扩展系数`），补充 HDD 场景 |
| 关键代码位置 | 缺少 `start_parsing` 和多文件循环位置 | 补充 L1522 文件循环、L1811 流式读取、L2874 snapshot_tiling_entry 调用点 |

### 10.2 补充的缺失内容

| 内容 | 说明 |
|------|------|
| `overall_offset` 恢复 | 跨文件 feature ID 唯一性的关键状态 |
| `initial_x` / `initial_y` / `initialized` 恢复 | 影响 `pool_off` 计算的关键状态 |
| `file_bbox` 累积恢复 | 各线程 `file_bbox` 和全局 `file_bbox` 的双重恢复 |
| `tree` / `node` 文件持久化 | 原方案遗漏了 tree memfile 和 node FILE* 的持久化 |
| memfile 恢复约束 | `memfile_full()` 单向性导致的恢复约束 |
| separator 对齐细节 | 流式模式块边界对齐 vs mmap 模式文件边界对齐 |
| 异常处理机制 | 新增 6.4 节，覆盖 checkpoint 写入异常、恢复异常、SIGTERM 处理 |
| v3.2 兼容性 | 明确当前代码版本为 v3.2，补充版本演进路径和兼容性矩阵 |
| 测试矩阵 | 新增 9.5 节，覆盖 Phase 1-3 的 30+ 测试用例和性能基准 |

### 10.3 优化的设计方案

| 优化点 | 说明 |
|--------|------|
| Phase 3 实现路径 | 区分流式模式（推荐，简单）和 mmap 模式（复杂，可选），降低实现风险 |
| `a4_index.bin` | 移除不必要的 index 持久化（中间产物，恢复时不需要） |
| layermap 序列化 | 明确复用 v3 `layermaps.bin` 格式，而非重新定义 |
| SIGTERM 处理 | 按子阶段细化处理策略，明确排序操作的原子性约束 |
| 磁盘空间评估 | 补充 HDD 场景的开销评估和禁用建议 |

### 10.4 关键技术决策

1. **流式模式优先**：Phase 3 优先实现流式模式的块边界 checkpoint，因为它天然支持线程同步（`pthread_join`），无需实现复杂的线程暂停/恢复机制。
2. **不持久化 index**：A4 的 index 是排序中间产物，恢复时只需要排序后的 geom，不保存 index 可节省磁盘空间。
3. **复用 v3 基础设施**：layermap 序列化、CRC32 校验、flock、SIGTERM、磁盘空间检查等均复用 v3 实现，减少开发量。
4. **渐进式实施**：Phase 1（A2-A5）→ Phase 2（文件边界）→ Phase 3（文件内）→ Phase 4（优化），每个阶段都有独立的收益。
